# OpenAI-compatible HTTP API

The `foxxycode http` subcommand ships only when the binary is built with **`go build -tags=http`** (`make build TAGS=http`). It exposes OpenAI-shaped routes plus **`/foxxycode/*`** helpers, backed by the same session manager and ReAct agent as **`foxxycode acp`**.

The bundled SPA is included only when you also set the **`ui`** tag (for example **`make build TAGS="http ui"`** or **`go build -tags=http,ui`**). With **http** only, **`GET /`** returns **404** with a plain-text hint.

**Checking before starting.** **`foxxycode http -t`** (long form **`--test-config`**) checks the config file a start would load against the embedded schema and the loader's rules, then exits without creating anything under the home. **`foxxycode http --dry-run`** runs that check, probes what the file points at and binds the listen address once - the one **`-H`**/**`-P`** select, or **`httpserver.host`**/**`httpserver.port`** when the flags are left alone - so a port another process holds is reported before a start trips over it. The editor plugins start this command, so their bundled binary answers both flags. Both exit 1 when something is wrong; details and sample reports are in [config.md](../getting-started/configuration.md#checking-the-file-from-the-command-line).

## OpenAPI and Swagger UI

Specs are regenerated on each request so they stay aligned with handlers.

- **`GET /openapi.yaml`** - OpenAPI 3.0 (YAML); **`GET /openapi.json`** mirrors it in JSON (both **`Content-Disposition: inline`**).
- **`GET /docs/`** - Swagger UI (static assets bundled in the binary, no CDN). **`GET /docs`** redirects to **`/docs/`**.

Swagger UI and the spec follow the API's authentication unless `httpserver.public_docs: true` ([Authentication & CORS](#authentication--cors)).

## Embedded web UI (**`-tags=http,ui`**)

- **`GET /`** serves **`index.html`**, **`styles.css`**, **`app.js`** and **`events-worker.js`** (the SharedWorker the tabs of one environment share **`GET /foxxycode/events`** through) from **`external/ui/`** (`go:embed`) when **`ui`** is set at link time with **`http`**. Responses for **`/`**, **`/index.html`**, **`/app.js`**, **`/events-worker.js`** and **`/styles.css`** include **`Cache-Control: no-cache`** so a normal reload picks up assets after you rebuild the binary (fixed URLs, no fingerprint).
- Recommended session URL pattern: **`#/s/<sessionId>`** (client-only history). For **`POST /v1/responses`** and **`POST /v1/chat/completions`**, send **`X-FoxxyCode-Session-ID`** with a **`sess_<hex>`** id that satisfies server-side validation (`internal/session/validate.go`).
- **`GET /foxxycode/sessions`**, **`PATCH /foxxycode/sessions/{id}`**, and other **`/foxxycode/sessions/{id}/...`** routes identify the session **only** by the **`{id}`** path segment (no duplicate header in OpenAPI; clients may still send **`X-FoxxyCode-Session-ID`**, it is not used to pick the resource for those URLs).
- The bundled UI calls **`POST /v1/responses`** with **`stream: true`**. On session open and reconnect, it reads **`GET /foxxycode/sessions/{id}/activity`** and **`GET /foxxycode/sessions/{id}/queue`** without requiring a row in the filtered or paginated **`GET /foxxycode/sessions`** listing. Server activity drives Stop and queue controls separately from the local stream reader; a lost reader does not prove the turn ended. The existing **`GET /foxxycode/sessions/{id}/composer-stream`** relay (SSE) lets the UI replay bytes already emitted for a running turn and continue receiving live chunks until **`data: [DONE]`** or an error event. Starting a new **`POST /v1/responses`** cancels that relay subscription client-side. For ReAct (**`model`** **`agent`**, **`plan`**, **`docs`**, **`ask`**, or **`debug`**), it sends optional **`metadata.model`** with the selected YAML **`models[].model`** **`id`** and optional **`metadata.runPlanSlug`** to implement a saved design plan (**`foxxycode.dev/runPlanSlug`** on ACP **`session/prompt`**; answered with **`409`** before the turn starts when **`model`** is **`ask`**) (from **`GET /v1/models`**, **`owned_by`** not **`foxxycode`**); default follows **`default_agent_model`**, persisted choice in **`foxxycode_llm_model`**. When the selected model exposes **`reasoning_levels`**, it also sends optional **`metadata.reasoning`** with the chosen level; default follows the model's **`reasoning_default`**, persisted choice in **`foxxycode_llm_reasoning`**. It derives **`attachments`** from **`@path`** mentions in **`input`** (files only); **`GET /foxxycode/workspace/files`** powers the **`@`** picker. SSE **default** chunks follow **`chat.completion.chunk`** deltas (**`delta.content`** for assistant text, **`delta.reasoning_content`** for streamed model reasoning so the UI can keep the **thinking** foldout separate). Named **`event:`** lines (**`tool_call`**, **`tool_call_update`**, **`plan`**, **`mode`**, **`token_usage`**, **`usage_update`**, **`available_commands`**, **`mcp_phase`**, **`llm_retry`**, **`message_queue`**, **`user_message`**, and **`debug`** when **`debug.enable`** is on) expose tool progress, incremental token totals between LLM rounds, and the current context-window occupancy; **`message_queue`** carries the whole message queue of the session on every change and **`user_message`** carries a queued follow-up the agent has just read, at the point it entered the conversation (see **`docs/features/message-queue.md`**); **`mcp_phase`** (**`{"phase":"connecting"}`** then **`{"phase":"ready"}`**) is emitted only when the turn has to wait for the session's configured MCP servers to finish connecting, and is transient status for the live label rather than a transcript row; **`llm_retry`** (**`{"phase":"waiting","attempt":1,"delayMs":60000}`** then **`{"phase":"retrying"}`**) is emitted only while a turn is parked between two attempts at the same model call because the provider produced no output at all (**`agent.llm_stall_retry`**), and is likewise transient status rather than a transcript row; when **`memory.enable`** is **true**, the server also emits **`memory_phase`** (**`sessionUpdate`** **`memory_phase`**) and **`memory_chunk`** (**`memory_message_chunk`**) for the unified memory copilot (**one pass before the main model**, recall-or-persist), streamed model text deltas only, without adding rows to **`messages.json`**. **`GET /foxxycode/sessions/{id}/messages`** may include **`memoryTurns`** (array of persisted per-turn summaries for the bundled UI transcript). **`foxxycode_meta`** JSON follows the usual rule immediately before **`data: [DONE]`**; for agent/plan/docs/ask/debug turns it also carries **`stop_reason`** (`end_turn`, `cancelled`, `max_turns`, ...) so remote clients recover the ACP stop reason. **Stop generation** in the composer calls **`POST /foxxycode/sessions/{id}/cancel`** with **`X-FoxxyCode-Session-ID`** matching **`{id}`**. Right after sending it, the UI triggers **`AbortSignal`** on its own streamed **`fetch`** of that turn (the POST or the relay): a browser keeps six HTTP/1.1 connections per host across all of its tabs, and the cancel could otherwise wait for the one that stream holds. The turn runs on without the stream; a failed cancel shows an error, keeps the running controls available for a retry and rejoins the turn through **`GET /foxxycode/sessions/{id}/composer-stream`**. That maps to ACP **`session/cancel`** for the agent turn (**`TurnCtx`** propagation for direct **`models[].model`** completions uses the same cancel hook). Cancel mid-stream still **persists** accumulated assistant **`content`** for that turn; **`GET /foxxycode/sessions/{id}/messages`** can briefly trail that write, so the SPA **merges** fetched rows with its per-session shadow or on-screen transcript (**`mergeTranscriptPreferLocalSuffix`** in **`external/ui/src/ui/chat/transcriptServerSnapshot.ts`**). More than one session may stream in parallel (**`pickStreamMutationBase`** in **`streamMutationBase.ts`** keeps SSE mutations scoped per **`X-FoxxyCode-Session-ID`**).
- A brand-new chat is named by the server: the title pass runs after the first exchange, persists the phrase and broadcasts **`session_title`**, so the UI only has to reload the session (**`sessionTitleSuggest.ts`** schedules a few refreshes). The same answer carries one to three **`tags`**, which are stored when the session has none yet - naming and filing a new chat cost one model call between them. **`POST /foxxycode/describe`** serves a client that names its sessions itself: it returns the phrase and the same **`tags`**, to be written back with **`PATCH /foxxycode/sessions/{id}`**. That PATCH takes **`titleIfUnpinned`**, which makes the title a suggestion: a session already named during the first turn - in the chat header, or by the agent's **`session_describe`** tool - keeps its name, and only the tags land.
- The bundled UI exposes **Settings** at **`#/settings`**. It loads **`GET /foxxycode/config/schema`** (JSON Schema for the editor) and **`GET /foxxycode/config`** (current values, including **API keys**, optional per-provider **`proxy`** URLs, and the **`gateways.telegram.token`** bot token), then **`POST /foxxycode/config/validate`** and **`PUT /foxxycode/config`** on save. The logical-model form additionally calls **`GET /foxxycode/providers/{name}/models`** behind **Fetch models** and **`GET /foxxycode/config/reasoning-levels`** behind **Fetch reasoning levels**, which fills **`models[].reasoning_levels`** with the tiers detected for the model id being edited (the type of the provider row it points at is sent as **`provider_type`**, so an unsaved provider is honoured). The **`gateways`** block round-trips through this API, so editing settings in the UI no longer drops the Telegram configuration. There is no separate auth on these routes - expose **`foxxycode http`** only on trusted networks.

- **Current context usage** is a separate named SSE event, **`usage_update`**, with **`used`** and **`size`**. It is re-emitted after manual or automatic compaction on **both** compaction engines (**`compaction.engine`** **`coddy`** / **`opencode`**), and once more when a session is reloaded from its bundle. **`token_usage`** remains the provider counter and is not used as the context-window numerator.
- **`token_usage`** counters are **cumulative for the turn**, not per model call: **`inputTokens` + `outputTokens` == `totalTokens`** in every event, and each event supersedes the previous one for that turn. **`GET /foxxycode/sessions/{id}/stats`** is the other half of the pair and reports **`tokenUsageTotal`** **cumulative for the session**, with **`tokenUsageByTurn`** holding the most recent turns (older ones are folded into **`tokenUsageTrimmed`** so the total stays whole). A client that renders a running total therefore adds the live **`token_usage`** of the current turn on top of the **`tokenUsageTotal`** it read **before** the turn started — it must not reseed that baseline from **`/stats`** while the turn streams, or the turn is counted twice.

## Endpoint summary

| Method | Path | Notes |
|--------|------|-------|
| GET | `/` | Embedded web UI (**`-tags=http,ui`**) or **404** with a hint (**`http` only**). **`Cache-Control: no-cache`** on **`/`**, **`/index.html`**, **`/app.js`**, **`/events-worker.js`**, **`/styles.css`** when the UI module is linked. |
| GET | `/openapi.yaml`, `/openapi.json` | Spec. |
| GET | `/docs`, `/docs/` | Swagger UI. |
| GET | `/v1/models` | Merged list: **`agent`**, **`plan`**, **`docs`**, **`ask`**, **`debug`** (each **`owned_by`**: **`foxxycode`**), then every YAML **`models[].model`** row (**`id`** is the selector; **`owned_by`** is the provider prefix). Ordering is **`agent`**, **`plan`**, **`docs`**, **`ask`**, **`debug`**, then **`models`** in configuration order. The JSON object also includes optional **`default_agent_model`**. Every row carries **`max_context_tokens`**, the context window a session on that model measures its usage and its automatic compaction threshold against: the model's **`max_context_tokens`**, else the window its provider's model listing reports, else **`128000`** (the profile rows carry the window of **`agent.model`**; the bundled UI draws its context ring against it). Model rows also carry **`multimodal`**, optional **`reasoning_levels`**, and optional **`reasoning_default`**. Codex-backed models report **`none`** where their model id would normally imply **`minimal`**, because the Codex backend rejects that tier. |
| POST | `/v1/chat/completions` | **`stream`**, **`messages`** (last **`user`**), optional **`stream_options.include_usage`**. With **`stream: true`** the body is the strict OpenAI **`chat.completion.chunk`** stream described under [Two stream dialects](#two-stream-dialects). **`409`** when another **agent**, **plan**, **docs**, **ask**, or **debug** turn already holds the session turn lock (exclusive per persisted bundle); the body carries **`error.code: "session_busy"`** plus **`error.sessionId`** and **`error.turnActive: true`** so a client can re-attach to the running turn via **`GET /foxxycode/sessions/{id}/composer-stream`** instead of dropping the request. With **`stream: true`** the request first waits up to **3s** for the lock, so a send issued right after **`POST /foxxycode/sessions/{id}/cancel`** is accepted while the cancelled turn finishes unwinding instead of being refused. Every **agent** / **plan** / **docs** / **ask** / **debug** turn is published to the session's composer relay whatever **`stream`** is set to, so other clients can watch it over **`GET /foxxycode/sessions/{id}/composer-stream`**; with **`stream: false`** the response body is unchanged. **`409`** also when **`X-FoxxyCode-Session-ID`** names a child session spawned by **`spawn_agent`**: those transcripts are read-only for every model kind, and the error names the parent session to prompt instead. |
| POST | **`/v1/responses`** | **`model`**, **`input`**, optional **`stream`**, optional **`attachments`** ( **`path`** workspace-relative under session cwd, **`agent`** / **`plan`** / **`docs`** / **`ask`** / **`debug`** only; file bodies are hydrated as text — a file stored in another detected encoding, such as Windows-1251, is converted to UTF-8; server rejects traversal, oversized, non-text (binary or undetectable encoding), and folder **`path`**; optional **`source.startLine`** / **`source.endLine`** narrow a file to a 1-based inclusive line range that the model sees as **`lines="N-M"`**, and a range the file cannot honour is a **`400`**), optional **`inline_files`** (array of **`{name, data_url}`**; **`data_url`** is a `data:<mime>;base64,...` URI; accepted for all modes **only when the effective YAML model has `multimodal: true`** — entries for a non-multimodal model are ignored and never forwarded to its provider). For **`agent`** / **`plan`** / **`docs`** / **`ask`** / **`debug`**: each file is saved to the session **`assets/`** directory (`~/.foxxycode/sessions/<id>/assets/`) with **`0o444`** (read-only) permissions; the model receives a `<foxxycode_session_assets>` annotation in the user message so it can `read` or `cp` the files without re-transmitting their bytes over the API. For direct YAML model: each entry becomes an image content part on the user message so multimodal models receive the file inline; it is persisted to the same **`assets/`** directory. Every decodable image also gets a bounded PNG thumbnail under **`assets/thumbnails/`**, which the transcript exposes as **`files[].preview_url`**. **`input`** remains the full composer text including **`@path`** echoes. Keeps history between turns when using headers. **`409`** when another **agent**, **plan**, **docs**, **ask**, or **debug** turn already holds the session turn lock; same **`error.code: "session_busy"`** / **`error.sessionId`** / **`error.turnActive`** envelope and the same up-to-**3s** wait for the lock on **`stream: true`** as **`/v1/chat/completions`**. Every **agent** / **plan** / **docs** / **ask** / **debug** turn is published to the session's composer relay whatever **`stream`** is set to, so other clients can watch it over **`GET /foxxycode/sessions/{id}/composer-stream`**; with **`stream: false`** the response body is unchanged. A **`stream: false`** turn is cancelled when its HTTP request is dropped; a streamed one keeps running. A streamed response that has produced no frame for 15s sends an SSE comment keepalive, so a turn on a YAML model with **`stream: false`** - silent on the wire until the whole answer is generated - is not dropped by an idle-timeout proxy. Note the two unrelated meanings of **`stream`**: this request field selects the response shape for the client, while **`models[].stream`** in **config.yaml** selects the transport FoxxyCode uses to reach the LLM. **`409`** also when **`X-FoxxyCode-Session-ID`** names a child session spawned by **`spawn_agent`**: those transcripts are read-only for every model kind, and the error names the parent session to prompt instead. |
| GET | `/v1/responses/{id}` | Session metadata snapshot. |
| GET | **`/foxxycode/sessions`** | Pagination via **`limit`/`cursor`** (cursor is numeric offset token). Optional **`q`** substring filter (**case-insensitive**) over **`session.json` title OR the **first persisted `user`** message **`content`** in `messages.json` order (`system`, `assistant`, `tool`, etc. before that first `user` are ignored). **`q` is not full-text search** over the transcript. Pagination applies **after** filtering. Rows sort by **`session.json` `updatedAt`** (newest first), then **`id`** for stable ties; **`updatedAt`** moves forward on persistence (new turns, title pin, etc.), not when the server only loads a bundle to serve **GET** requests. **`include_scheduler=true`** includes session bundles created for **scheduler runs** (they set **`schedulerRun`** in **`session.json`** and are **omitted** from the default composer list). **`include_activity=true`** adds **`turnActive`**, **`activitySeq`**, **`readActivitySeq`**, and **`unreadComplete`** to each row for multi-tab UI. **`include_stats=true`** adds what the session management table renders: **`messageCount`** (persisted transcript rows of every role), **`tokenUsage`** **`{inputTokens, outputTokens, totalTokens}`** read from the bundle's **`stats.json`** (zeroes for a session that never completed a model call), **`createdAt`** and **`model`**. **`createdAt`** is **omitted** for a bundle stored before the field existed - when a session was started is not recoverable and is not invented - and **`model`** is **omitted** for a session that never overrode **`agent.model`**, so a client shows those as unknown instead of as a value. The listing itself reads only each bundle's **`session.json`**; the message count and token usage are read for the rows of the returned page alone. Optional **`cwd`** (absolute directory) keeps only sessions whose **`cwd`** is that directory or lies beneath it, compared as folders rather than strings (cleaned, symlinks resolved, case-insensitive on Windows and macOS); it is applied **before** **`q`** and pagination. The IntelliJ / VS Code plugins pass the open project root here so History lists that project only — a session running in a **linked worktree outside the project root** (one made by hand elsewhere, or an SVN branch folder under **`<home>/worktrees/<wc>`**) is excluded and needs the unscoped call, while the git worktrees FoxxyCode creates live under **`<repo>/.foxxycode/worktrees/`** and stay in scope. **`include_subagents=true`** includes child sessions spawned by **`spawn_agent`** (**`subagentRun`** in **`session.json`**, stored inside the parent's bundle and hidden by default); each such row carries **`subagent`** **`{parentSessionId, name, taskId}`** read from that bundle, and the default listing never descends into one. Optional **`archived`** selects which side of the archive is listed: **`exclude`** (the default working list), **`only`** or **`all`**; a row that is archived carries **`archived: true`** and **`archivedAt`**. Optional **`tags`** is a comma separated list and keeps the sessions carrying **any** of them, normalized the way stored tags are, so **`Backend`** finds **`backend`**; a row carries its **`tags`** when it has any. Optional **`origin`** keeps the sessions of one surface: **`local`** for the ones opened on this host, **`gateway`** for the chats a messenger gateway is holding; a row started by a gateway carries **`origin`** (**`gateway:telegram`**). Optional **`sort`** (**`updated`** by default, or **`created`**, **`title`**, **`messages`**, **`tokens`**) and **`order`** (**`desc`** by default, or **`asc`**) replace the default ordering; they are applied to the **whole filtered listing before paging**, so page two of a sorted listing continues page one. A **pinned** session leads the listing whatever **`sort`** says, and the pins are ordered among themselves by **`pinnedRank`** - the order the operator dragged them into - newest pin first until one is dragged. A session the sort column says nothing about (no creation stamp, no title) sorts **last in both directions**, ties break by id, and **`tokens`** reads each bundle's **`stats.json`**, so it costs one extra small file read per session and only when it is the column asked for. An unknown **`archived`**, **`origin`**, **`sort`** or **`order`** value is a **`400`** rather than a silent default. In this fork **`cwd`** keeps the sessions of a folder **and everything below it**, and it is applied before **`sort`**; **`sort=messages`** is the one ordering that opens transcripts, and only when it is asked for - a plain listing reads **`session.json`** alone. |
| POST | **`/foxxycode/describe`** | JSON **`{"text"}`** to get a short description phrase and the **`tags`** the model proposed for filing the conversation. The tags ride on the call that already names a new chat, so a session is filed without a second request to the model; a model that ignores the instruction answers the phrase alone and **`tags`** is an empty array. Every text is asked about, however short: a first message of two words is the one that needs the labels most. |
| POST | **`/foxxycode/enhance-prompt`** | JSON **`{"text"}`** — rewrites the user's draft prompt into a clearer, more specific one via a single direct LLM completion (no tools). The draft is treated only as source text to improve, never as a request to answer. Optional **`X-FoxxyCode-Session-ID`** selects the rewrite model: the session's effective model (same one the chat uses), falling back to **`agent.model`** and then the first configured **`models[]`** row. Unknown or invalid ids fall back silently and never create a session. JSON **`{"object":"foxxycode.enhance_prompt","text"}`**; **`400`** on blank text, **`502`**/**`503`** on LLM error/unavailability (including no model configured). The composer wand button (**`data-testid="composer-enhance-btn"`**) calls this and replaces the draft; **Ctrl+Z**/**⌘Z** restores the pre-enhance text, and failures surface in **`composer-enhance-err`** instead of silently doing nothing. |
| GET | **`/foxxycode/slash-commands`** | Paginated slash commands derived from configured skills (**`page`**, **`page_size`** required). Optional **`prefix`** filters by **`name`** (case-insensitive). Optional **`X-FoxxyCode-Session-ID`** resolves **`${CWD}`** expansion for **`skills.dirs`** like other session-scoped lookups. JSON **`items[].name`** and **`items[].description`**, **`total`**, **`has_more`**. The deterministic built-in commands (**`/compact`** while compaction is enabled, **`/export`**, **`/plugin`**) lead the catalogue, ahead of the skill rows, and **`prefix`** filters them like any row; **`/foxxycode/commands`** lists them on their own, the ACP available-commands update advertises them to editors, and they run without an LLM turn when sent as a prompt (e.g. **`POST /v1/responses`** with **`input:"/plugin marketplace list"`**). |
| GET | **`/foxxycode/commands`** | Lists the deterministic built-in slash commands (**`/compact`**, **`/export`**, **`/plugin`**) that run without an LLM turn on their own, without the skills; the remote console (**`--remote`**) merges it with **`/foxxycode/slash-commands`**, which leads with the same rows. Optional **`prefix`** filters by **`name`** (case-insensitive). JSON **`{"object":"foxxycode.commands","items":[{"name","description"}]}`**. **`compact`** is included only while **`compaction.enable`** is true (both engines answer it); **`export`** and **`plugin`** are always present. **`/export`** sent as a prompt writes the session transcript to a file in the session workspace (see **`docs/session-export.md`**). |
| GET | **`/foxxycode/skills`** | Lists all skills found in configured **`skills.dirs`**. Optional **`X-FoxxyCode-Session-ID`** resolves **`${CWD}`** in **`skills.dirs`** against that session's workspace, like **`/foxxycode/slash-commands`** (server default cwd without the header; **`400`** for a malformed id, **`404`** for an unknown session). JSON **`{"object":"foxxycode.skills_list","items":[...]}`**; each item has **`name`**, **`description`**, **`file_path`**, **`enabled`**, **`version`** (installed version — the marketplace-declared version for synced skills, else the **`SKILL.md`** frontmatter version; absent when unknown), **`source`** (the configured **`skills.sources`** entry when the skill was installed remotely; absent for local/bundled skills), and **`readonly`** (**`true`** for bundled skills, which cannot be deleted). Uses same directory scan and last-wins deduplication as the agent loader. |

Invalidates the slash-command cache so the next **`/foxxycode/slash-commands`** call reflects the change. |
| POST | **`/foxxycode/skills/{name}/disable`** | Adds **`{name}`** to the disabled list. Same response codes and cache invalidation as **`enable`**. |
| POST | **`/foxxycode/skills/sync`** | Fetches configured skill sources and materializes skills into **`ManagedDir`**. Without **`source`**, syncs every entry in **`skills.sources`**; with **`?source=<src>`**, syncs only that marketplace (a GitHub repo, git URL, or **`marketplace.json`** URL, whether or not it is in the config). | GET | **`/foxxycode/skills/updates`** | For every installed remote skill, fetches its marketplace source and compares the installed version against the latest declared upstream (network / git access). **`200`** **`{"object":"foxxycode.skills_updates","items":[{"name","source","version","latest","update_available"}]}`**. |
| GET | **`/foxxycode/skills/available`** | Fetches every configured marketplace manifest (network / git) and lists the plugins they advertise for install. **`200`** **`{"object":"foxxycode.skills_available","items":[{"name","description","version","source","installed"}]}`**. |
| POST | **`/foxxycode/skills/install`** | JSON **`{"source","plugin"}`**: installs a single named plugin from a marketplace source (not the whole source). **`200`** **`{"ok":true,"added":[...],"updated":[...],"failed":[...]}`**; **`400`** when the plugin or source is unknown. | POST | **`/foxxycode/skills/{name}/update`** | Re-syncs the marketplace source that provides **`{name}`**, installing the version it currently declares. **`200`** **`{"ok":true,"added":[...],"updated":[...],"failed":[...]}`**; **`400`** when **`{name}`** was not installed from a remote source. ### Stop and queue control snapshots

On session open and reconnect, clients read **`GET /foxxycode/sessions/{id}/activity`** and **`GET /foxxycode/sessions/{id}/queue`** for the selected id. These reads do not depend on a matching row in a filtered or paginated History listing, a live turn reader, or another queue mutation. The UI and interactive remote console track server activity separately from their own prompt/stream lifetime. The browser skips both hydration reads during its own POST admission and confirms a **`turn_ended`** overlapping a pending or admitted POST through fresh REST before declaring idle.

The session manager's **`QueueSnapshot`** reads the queue list and its **`version`** under one lock. Queue HTTP responses (**GET**, **POST**, and **DELETE**) and **`message_queue`** events use that pair, so a response cannot label an older list with a newer version. Ordinary deliveries keep the highest version per session. For browser restart recovery, a fresh queue GET captures the delivery revision and recovery epoch before the request. The browser rejects a snapshot crossed by any queue delivery; otherwise it may establish a lower version, including **`0`**. That recovery advances the local epoch and rejects mutation responses and own/relay stream queue frames captured in earlier epochs. Replayed **`turn_started`** notifications do not clear the waiting list or reset its version.

These controls retain the existing routes, JSON shapes, and status codes. They do not change non-interactive prompt handling or permission/question ownership, and do not attach the remote console to another client's live transcript. Shared queues require clients of the same **`foxxycode serve`** process; separate local console or ACP processes sharing only a sessions directory retain separate queues and answer channels. Cross-process cancellation still uses the bundle's cancel marker.

### Two stream dialects

The two streaming endpoints carry the same turn in two shapes, chosen by who reads them. **`POST /v1/chat/completions`** with **`stream: true`** is the surface a third-party client points at (VS Code Copilot through `chatLanguageModels.json`, the openai SDKs, anything that parses `chat.completion.chunk` literally), so it is the strict OpenAI contract and nothing else: a first chunk with **`delta.role`** `assistant`; **`delta.content`**, **`delta.reasoning_content`** and **`delta.tool_calls`** deltas, each choice with **`finish_reason: null`**; a final chunk whose **`finish_reason`** is **`stop`**, **`length`** when the turn ended on **`max_turns`** / **`max_tokens`**, **`tool_calls`** when a direct model called one of the client's tools, or **`content_filter`** when the provider's content filter cut a direct answer short; with **`stream_options.include_usage: true`** one more chunk with an empty **`choices`** array and the turn's **`usage`** (**`prompt_tokens`**, **`completion_tokens`**, **`total_tokens`**, from the provider's own counters, zero when it reported none); then **`data: [DONE]`**. No named **`event:`** frame appears on it - such a client would read one as a chunk without choices - though each leaves an SSE comment in its place, so the connection stays as busy as the turn through a tool phase; a turn that produced no text still opens and finishes one choice, because a stream that never finishes a choice is what VS Code reports as "Response contained no choices." **`POST /v1/responses`** is foxxycode's own channel, read by the SPA, the remote console (**`--remote`**, **`foxxycode acp --remote`**) and the swarm relay: the same chunks plus every named event below, **`foxxycode_meta`** last.

  A direct **`models[].model`** id on **`POST /v1/chat/completions`** is foxxycode standing in for the provider, and the client brings what it would bring to the provider. Its **`tools`** (OpenAI function tools) are offered to the model as they are; **`tool_choice`** `none` withholds them, and any other value leaves the choice to the model, because the providers take no forcing parameter. A call the model makes comes back as **`delta.tool_calls`** chunks on the stream - one chunk per call, arguments complete, **`index`** counting the calls - and as **`message.tool_calls`** on a JSON answer, with **`finish_reason`** **`tool_calls`**; the client runs the tool, replays the assistant message with its **`tool_calls`** and answers with a **`tool`** message under the **`tool_call_id`**, and that request may end on the tool message. Message **`content`** may be a string, `null` or an array of parts: **`text`** parts are joined, **`image_url`** parts (a data URL or an https address) reach a model whose **`models[].multimodal`** is true as images and are dropped for any other model, never flattened into text; they are accepted on user messages only, as at OpenAI, and refused with **`400`** on any other role, as are other part types. What a client may hand over is bounded: at most 128 tools, a tool's **`parameters`** up to 256 KiB, 16 images per message and 20 MiB per image URL string (a data URL carries the picture itself), past which the request is refused with **`400`**; an https image address is handed to the provider as it is, foxxycode never fetches it. A JSON answer made of tool calls has **`content`** `null`, as OpenAI renders it. The **agent** / **plan** / **ask** profiles run foxxycode's own tools and never read the client's, and take no trailing **`tool`** message, though the pictures of the last user message reach a multimodal profile model. An **agent** / **plan** / **ask** turn started over either endpoint is published to the composer relay in the rich shape whatever the caller received, so a browser watching the session sees its tool calls either way.

## **`model`**, profiles, and direct completion

- **`POST /v1/chat/completions`** and **`POST /v1/responses`** require **`model`** to be exactly one **`id`** from **`GET /v1/models`** (session operating profiles **agent** / **plan** / **docs** / **ask** / **debug** or a **`models[].model`** entry).
- **agent** / **plan** / **docs** / **ask** / **debug** selects the FoxxyCode agent (ReAct, tools). Optional JSON **`metadata.model`** updates the session model selector, and **`metadata.reasoning`** updates its supported reasoning level. The agent maps the level to OpenAI **`reasoning_effort`**, Anthropic extended-thinking **`budget_tokens`**, or Codex **`reasoning.effort`** (`minimal` becomes `none`) with reasoning summaries and encrypted replay.
- **`model`** listing a **`models[].model`** YAML selector runs **one direct LLM request** per call (no ReAct); **`metadata`** with a **`model`** key on that branch is rejected with **400** (use **`model`** as the routing field only).
- On **`POST /v1/chat/completions`** a direct model takes the generation options of the request for that one request. **`max_tokens`**, or its newer OpenAI name **`max_completion_tokens`** (a request may carry both only when they agree), replaces the model's **`max_tokens`**, and **`temperature`** replaces its **`temperature`**, **`0`** included. Without them the configured values apply, and no request changes the configuration or leaks into another request. A value the provider cannot send as asked is refused with **400** before a session is created or the provider is contacted: a cap below 1, a temperature outside 0-2 (0-1 for an **`anthropic`** provider), and either option on a **`codex`** model, since the Codex backend rejects both. A requested temperature is sent next to a reasoning level as well, where a configured one is left out: whether the model takes both is the backend's answer (Qwen3 thinking on vLLM does, OpenAI's reasoning models refuse).
- **`reasoning_effort`** on the same request picks the reasoning level, and it must be one of the **`reasoning_levels`** **`GET /v1/models`** lists for that id; any other value, or any value for a model that lists none, is **400**, never a quiet downgrade. Omitted, **`null`** or **`""`**, the model's **`reasoning_default`** applies, and a model without a default gets no reasoning parameter at all - not the same request as the level **`none`**, which a **`codex`** model offers and receives as such. The level travels as OpenAI **`reasoning_effort`**, as Anthropic extended thinking (where a **`max_tokens`** of the request that leaves no room above the thinking budget is **400** rather than silently raised) or as Codex **`reasoning.effort`**, and the JSON answer reports it as **`metadata.reasoning_effort`**.
- The **agent** / **plan** / **docs** / **ask** / **debug** profiles read none of these fields: a profile turn is a series of LLM calls, each on the profile model's configured values, and its reasoning level comes from **`metadata.reasoning`**.
- A direct answer is finished only by the provider's own terminal signal: a **`finish_reason`** or **`[DONE]`** from an OpenAI-compatible server, a **`stop_reason`** from Anthropic, **`response.completed`** or **`response.incomplete`** from Codex. Codex's **`response.incomplete`** keeps the text written so far and reports its reason (**`max_output_tokens`** as **`finish_reason`** **`length`**, **`content_filter`** as **`content_filter`**; any other reason is an error), and **`response.failed`** is an error carrying the backend's code and message. A stream that closes before any terminal signal is an error naming the truncation (**`500`** on a JSON answer, an error frame and no finished choice on a stream), never a **`stop`**, and a failure after text reached the client is not retried into a second copy of it.

Non-stream replies include **`metadata`** with **`model`** set to the effective YAML backend selector (**`api_model`** may expose the REST model id).

## Sessions and headers

### Without **`X-FoxxyCode-Session-ID`**

`POST /v1/chat/completions` / **`POST /v1/responses`** allocate a random session bundle for that flow (ACP **`session/new`**). The bundle's working directory is the **current project** (**`GET /foxxycode/project`**) when one is set, else the process default cwd. An explicit **`-cwd`** flag / **`FOXXYCODE_CWD`** at startup seeds the current project; otherwise the last opened project is restored from `~/.foxxycode/projects.json`.

### With **`X-FoxxyCode-Session-ID`**

1. Active in-memory bundle wins.
2. Otherwise load from disk when **`session.json`** exists.
3. Otherwise pin **`session/new`** with the supplied identifier (fresh empty bundle folders).

Malformed ids (**HTTP 400**). Dedicated **`/foxxycode/*`** helpers return **503** if persistence is unavailable (`Manager` lacked a **`FileStore`**, primarily in tests).

### Per-session mode and model (bundled UI)

- **`GET /foxxycode/sessions/{id}/messages`** returns **`mode`** (stored session profile: **`agent`**, **`plan`**, **`docs`**, **`ask`** or **`debug`**), **`model`** (effective YAML backend for the session), **`selectedModelId`** (stored override in **`session.json`**, may be empty), and **`selectedReasoning`** (effective reasoning level for the session, empty when the model has none).
- **`PATCH /foxxycode/sessions/{id}`** accepts **`mode`** to set the session profile (anything outside the five profiles **400**), **`selectedModelId`** to set the YAML **`models[].model`** selector for that session (unknown ids **400**) and **`selectedReasoning`** to set the reasoning level (must be one of the model's **`reasoning_levels`**; empty clears it; unsupported value **400**).
- The SPA restores **Model** from **`model`** and **Mode** from **`mode`** when opening a chat; a **New chat** starts in **`agent`**. Changing **Model** writes cookie **`foxxycode_llm_model`** (default for the next **New chat**) and **`PATCH`**es the active session; changing **Mode** **`PATCH`**es **`mode`** so the profile survives a reload even when no turn was sent. A turn writes the profile too, through the top-level **`model`** of **`POST /v1/responses`**.
- When the **server** changes the profile - **`metadata.runPlanSlug`** switching a plan run back to **`agent`**, or the model calling **`plan_exit`** - the turn's stream carries the named SSE event **`mode`** (**`{"sessionUpdate":"current_mode_update","currentModeId":"agent"}`**). It also replays through **`GET /foxxycode/sessions/{id}/composer-stream`**, so a client that reconnects mid-turn still sees it. A client that ignores this frame keeps posting the profile the session has already left, and the next turn writes that stale profile back.

## Authentication & CORS

Off by default (unchanged "no login" behavior). When **`httpserver.auth_token`** (or **`--auth-token`** / **`FOXXYCODE_HTTP_TOKEN`**) is set, every **`/v1/*`** and **`/foxxycode/*`** route requires **`Authorization: Bearer <token>`** and returns **`401`** with **`WWW-Authenticate: Bearer`** otherwise. The SPA shell and static assets stay public; **`/docs`** and **`/openapi.*`** are protected unless **`httpserver.public_docs: true`**; the local IDE-integration routes (**`/foxxycode/ide/*`**) answer a direct loopback client without a credential, which is how the editor plugins call them, and ask everyone else for one. A browser can sign in at a form instead of carrying a token: see [Web UI sign-in](#web-ui-sign-in-optional). The token is redacted from **`GET /foxxycode/config`** (reported only as **`auth_configured`**) and preserved on **`PUT`** when the payload omits it. Because EventSource cannot set an Authorization header cross-origin, the two SSE subscription routes - **`GET /foxxycode/sessions/{id}/composer-stream`** and **`GET /foxxycode/events`** - also accept **`?access_token=`**. A query string reaches access logs, proxy logs, browser history and `Referer` headers, so prefer a **stream ticket**: **`POST /foxxycode/stream-tickets`** (authenticated with the normal bearer header) returns **`{object, ticket, expiresIn, expiresAt}`**, and that ticket is accepted by the two SSE routes only, once, within 60 seconds. Set **`httpserver.stream_tickets_only: true`** to refuse the durable token in **`?access_token=`** entirely, so nothing that lands in a log stays valid.

Switches in the JSON body are named **`enable`**, the same as in `config.yaml`; **`enabled`**, the name used before 0.3.x, is still accepted and answered as **`enable`**.

Cross-origin access for a browser UI on another origin is controlled by **`httpserver.cors`** (**`enable`** + **`allowed_origins`**, a single **`"*"`** allows any origin; bearer auth still applies). Preflight **`OPTIONS`** returns **`204`** before auth. The bundled UI can point at a remote **`foxxycode http`** via the environment selector (**`httpserver.remotes`**). See [remote-control.md](../plans/remote-control.md).

### Web UI sign-in (optional)

A bearer token protects the API but gives a browser no way in: the SPA shows `Unauthorized (401)`
and has no field to type a token into. The sign-in form is the browser's credential for the same
gate. It is **off by default**, and a configuration that does not mention it behaves exactly as
before.

```yaml
httpserver:
  host: 0.0.0.0
  auth_token: "${FOXXYCODE_HTTP_TOKEN}"   # unchanged: for API clients
  login:
    enable: true
    user: "pasha"
    password_hash: "$$argon2id$$v=19$$..."   # written by `foxxycode serve set-password`
    session_ttl_hours: 720                   # 0 = until the browser closes
```

Write the account with the command rather than by hand:

```bash
foxxycode serve set-password --user pasha
```

It asks for the password twice (once, without a prompt, when standard input is a pipe), stores an
argon2id hash and switches the form on, editing `config.yaml` in place so comments and key order
survive. A hash typed in by hand needs every `$` doubled - `$$argon2id$$v=19$$...` - because this
file expands `$NAME` as an environment reference when it loads; `foxxycode -t` says so when it finds a
hash that no longer parses.

The account can also live entirely in the environment, which is the route for a container or a
systemd unit: `FOXXYCODE_HTTP_USER` and `FOXXYCODE_HTTP_PASSWORD` (plaintext, hashed as the server starts,
never written to the file) enable the form on their own, the way `FOXXYCODE_HTTP_TOKEN` enables the
bearer gate without `auth_token`. `$FOXXYCODE_HOME/.env` is their natural home. When both the file and
the environment carry an account the environment wins, and an explicit `login.enable: false` in the
file switches the form off with the variables still set. There is no `--login-password` flag: a
password on a command line is visible in `ps`.

Three routes serve the form, and all three are reachable without a credential, because they are the
way through the gate:

| Route | What it does |
|---|---|
| **`GET /foxxycode/auth/me`** | `login_required`, `auth_required`, `authenticated`, and `user` / `expires_at` for a signed-in browser. The SPA calls it on boot to choose between the sign-in screen and the app. |
| **`POST /foxxycode/auth/login`** | `{user, password}`. On success sets an `HttpOnly`, `SameSite=Strict` `foxxycode_session_<host digest>` cookie (`Secure` when the request arrived over TLS or through a proxy sending `X-Forwarded-Proto: https`), living for `session_ttl_hours`; with `0` the browser drops it on close and the server expires its own record after 30 days. The name carries a digest of the host the request was addressed to, because cookies are not scoped by port: without it two FoxxyCode servers on one machine - a relay and the node behind it, say - would sign each other out at every login. |
| **`POST /foxxycode/auth/logout`** | Drops the session on the server and expires the cookie. Idempotent. |

Once signed in, the cookie opens every `/v1/*` and `/foxxycode/*` route, the SSE streams included - a
same-origin `EventSource` sends cookies, so no `?access_token=` is needed. The cookie is
`SameSite=Strict`, which costs nothing here (the page itself is public and every call the loaded
page makes is same-origin) and means the browser never attaches it to a request another site caused.
On top of that, cookie-authenticated requests that **change state** are refused with `403` unless
`Sec-Fetch-Site` says `same-origin` (or `none`) or `Origin` matches the request host - so a script
driving this API with a cookie has to send an `Origin` header, or, better, present a bearer token.
Bearer requests are never subject to that check, which is what keeps `foxxycode --remote`, an editor and
a relay working unchanged.

A wrong password and an unknown user get the same `401` and the same body, compared in constant
time. Repeated failures from one address are answered progressively more slowly, doubling from
250 ms to a cap of five seconds and forgotten after fifteen quiet minutes; the attempt is counted
before it is judged, so a burst arriving together pays the growing wait rather than each member
reading a clean slate. Loopback is never throttled, so the machine cannot lock itself out of its own
agent - and because that exemption would otherwise cover the whole internet behind a reverse proxy,
a request that arrives *from* loopback is counted against the address in `X-Forwarded-For` (or
`X-Real-IP`) when one is present. A request that arrives from anywhere else is counted by where it
actually came from, headers ignored. Sessions live in memory: a
configuration reload (saving settings from the page, for instance) keeps them, and restarting the
process ends them. Rotating the password or renaming the account ends every session it opened, on
the next request, with nothing to invalidate by hand. The store is bounded at 512 live sessions,
oldest first.

`GET /foxxycode/config` never returns `password_hash`; it reports `httpserver.login_configured` and
`httpserver.login_source` (`config` or `env`), and a save from the settings screen preserves the
hash the way it preserves `auth_token`. The neighbouring `auth_configured` means what it says - a
bearer token is set - so a server closed with a password and no token reports
`auth_configured: false` next to `login_configured: true`; ask `GET /foxxycode/auth/me` when the
question is "does this server want a credential at all". The document keeps describing the file, so an account that
came from the environment is never written into `config.yaml` by a save.

On `foxxycode http` - the command the IntelliJ and VS Code plugins and `foxxycode desktop` start on `127.0.0.1` - a direct loopback client (the peer and the `Host` it addressed are both loopback, and no `Forwarded` / `X-Forwarded-*` / `X-Real-IP` header says a proxy relayed it) counts as signed in while no bearer token is configured, so the editor panels and the desktop window never meet the form; `GET /foxxycode/auth/me` answers it `login_required: false`. A client on the network still signs in, and `foxxycode serve` makes no such exception. The IDE routes (`/foxxycode/ide/*`) follow the same loopback rule on every server: without a credential they answer a direct loopback client only.

The sign-in form is for this origin. The environment selector still reaches a **remote** server with
a bearer token, because a cookie of this origin does not travel cross-origin.

One note on `${VAR}` references. `login.user` and `login.password_hash` take them like every other
value in `config.yaml`, and like every other value they are expanded when the file loads - so a save
from the settings screen writes the **expanded** value back, turning `user: "${FOXXYCODE_HTTP_USER}"`
into `user: pasha`. That is how this file has always treated `${VAR}`; if the point is to keep the
credential out of the document entirely, use `FOXXYCODE_HTTP_USER` and `FOXXYCODE_HTTP_PASSWORD`, which
never enter it.

## Memory roots

Matches `external/memory/README.md`: **`global`** uses configured **`memory.dir`** (fallback **`$FOXXYCODE_HOME/memory`**). **`workspace`** resolves to **`$CWD/memory`** for that session bundle. **`agentMemory`** placeholders remain agent-only (`session.json`), not REST-editable here.

Interactive tool permission prompts are bypassed when **`tools.permission_mode`** is **`bypass`**. Otherwise the bundled UI shows **`event: permission`** during **`POST /v1/responses`** (**`stream: true`**) and completes the turn via **`POST /foxxycode/sessions/{id}/permission`** (same pattern as **`question`**).

## CLI flags

Equivalent to **`foxxycode acp`**: **`--config`**, **`--home`**, **`--cwd`**, **`--sessions-dir`**, **`--session-id`**, **`--log-*`**, optional **`--scheduler-enabled`**. Networking flags: **`-H` / `--host`**, **`-P` / `--port`**. Defaults fall back to YAML **`httpserver.host` / port** when left at **`0.0.0.0:12345`**.

## Build

```bash
# HTTP API only (no npm, no embedded SPA root)
make build TAGS=http

# HTTP API plus embedded SPA (**make ui-build** runs first)
make build TAGS="http ui"
```

`go test ./...` skips **`external/httpserver`** unless **`go test -tags=http`**. SPA-specific tests compile under **`go test -tags=http,ui`** (Makefile **`make test`** runs **`ui-build`** once, then a single pass with every optional module compiled in; **`make test-matrix`** and CI walk **`http`**, **`http,ui`** and the scheduler combinations one job at a time).

For a manual gateway check against a disposable **`foxxycode http`** process, **`examples/test_httpserver.sh`** runs the Python demos under **`examples/httpserver/`** (see **`examples/README.md`**). Steps that call chat or responses expect a working **`models`** backend.
