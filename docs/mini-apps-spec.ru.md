# Спецификация мини-приложений FoxxyCode

Статус: продуктовое и архитектурное предложение для первой реализации.

Английская версия: [mini-apps-spec.md](mini-apps-spec.md)

Проверяемые продуктовые требования:
[mini-apps-functional-requirements.ru.md](mini-apps-functional-requirements.ru.md).

## 1. Назначение

Мини-приложение FoxxyCode — это переносимая программа с операторским
интерфейсом, дистиллированная из успешной сессии FoxxyCode. Она превращает
задачу, выполненную интерактивно с агентом, в воспроизводимый workflow, который
можно позднее запускать без исходной сессии и без принятия каждого решения
универсальным агентом.

Основной пользовательский сценарий:

1. Сотрудник выполняет задачу в обычной сессии.
2. Сотрудник нажимает **Создать мини-приложение** для этой сессии.
3. FoxxyCode анализирует сессию, выделяет один конкретный успешный сценарий,
   находит значения, которые должны стать входами, и создает редактируемый
   черновик.
4. Пользователь проверяет сгенерированную форму, workflow, зависимости,
   разрешения, критерии успеха и представление результатов.
5. FoxxyCode тестирует черновик на тех же фактических данных, что использовались
   в исходной сессии, и итеративно улучшает его до прохождения объявленных
   критериев успеха.
6. Человек проверяет очищенный bundle и выпускает релиз.
7. Оператор запускает релиз через FoxxyCode или совместимый автономный
   интерпретатор.

Мини-приложения должны сокращать повторную агентскую работу, расход токенов,
время выполнения и требования к знанию промптов или программирования при
рутинных операциях.

## 2. Объем продукта

### 2.1 MVP

Первая реализация включает:

- явное действие **Создать мини-приложение** для завершенной сессии;
- раздел **Мини-приложения** в веб- и десктопной навигации;
- дистилляцию сессии в редактируемый черновик;
- структурированный workspace дистилляции с упорядоченным навигатором шагов,
  временными source evidence и authoring-only refinement assistant;
- автоматически определяемые операторские входы и элементы формы;
- версионируемый JSON-язык workflow с универсальным стековым шагом
  `foxxy-vm/1`;
- последовательное выполнение, условия, retry, fallback и композицию через
  вызов другого мини-приложения;
- детерминированные скрипты, внешние команды, агентские циклы, HTTP API-вызовы,
  вызовы MCP и включенных в bundle skills, файловые операции, ввод оператора и
  явное подтверждение оператора;
- inline-скрипты и файлы в bundle;
- объявляемые системные зависимости и скрытую приватную установку
  зафиксированных portable runtime, пакетов и локальных моделей;
- выбор по возможностям либо фиксированную привязку provider/model, включая
  обнаружение локального провайдера и объявленный bootstrap модели;
- тестовый запуск с теми же фактическими данными исходной сессии;
- настраиваемые детерминированные и модельные проверки результата;
- очистку черновика и обязательную проверку человеком перед релизом;
- состояния `draft` и `released`;
- импорт и экспорт переносимых bundle;
- компактный поисковый drawer мини-приложений из открытой web/desktop-сессии в
  дополнение к полному разделу каталога;
- режим интерпретатора FoxxyCode, запускающий `miniapp.json` или bundle без web
  UI;
- builder, создающий один executable с интерпретатором, JSON-программой,
  выбранными UI-ресурсами и полным bundle;
- выбираемый оператором режим собранного приложения: console или desktop UI;
- историю запусков, входы, выходы, логи, длительность, отмену и повтор;
- метрики длительности и использования модели для source/test/run, когда
  provider их предоставляет;
- ручной выбор пользователя между повторным использованием мини-приложения,
  созданием новой версии и продолжением обычной агентской сессии.

### 2.2 Явно не входит в MVP

- автоматическая фоновая дистилляция всех сессий;
- использование в IntelliJ, VS Code, ACP или других IDE-интерфейсах;
- автоматическая трехсторонняя маршрутизация или автоматическое сравнение
  вариантов «сделать с нуля», «адаптировать мини-приложение» и «запустить
  обычного агента»;
- автоматический организационный сбор без явного согласия;
- параллельные ветви workflow;
- скрытая системная установка зависимостей, повышение привилегий или скрытое
  расширение разрешений.

Схема резервирует точки расширения для будущей маршрутизации и поиска, но MVP
не выбирает путь за пользователя автоматически.

## 3. Поддерживаемые интерфейсы продукта

Создание, редактирование, релиз, просмотр каталога и интерактивный запуск
мини-приложений доступны только:

- во встроенном веб-интерфейсе, обслуживаемом `foxxycode http`;
- в десктопном приложении FoxxyCode.

IDE-интеграции не должны показывать действие **Создать мини-приложение** или
раздел **Мини-приложения**. HTTP API и автономный интерпретатор могут
использоваться клиентами автоматизации вне IDE.

Поддержка мини-приложений является опциональным compile-time модулем и
включается Go build tag `miniapps`:

- с `miniapps` FoxxyCode содержит интерпретатор, builder executable,
  mini-app HTTP routes и runtime capability `miniapps`;
- без `miniapps` соответствующие CLI-команды и HTTP routes не регистрируются, а
  capability имеет значение false;
- web/desktop UI показывает действие сессии, каталог, editor и runner только
  после получения этой capability от backend;
- IDE-интерфейсы продолжают скрывать функциональность, даже если их backend
  собран с этим tag.

Решение о видимости должно приходить из backend capability, а не из
захардкоженного предположения frontend-сборки. Встроенная SPA не должна
показывать controls, которые не поддерживает запущенный binary FoxxyCode.

## 4. Термины

| Термин | Значение |
|--------|----------|
| Исходная сессия | Сессия, временно анализируемая для создания черновика. |
| Дистилляция | Преобразование сессии в параметризованный workflow и его тестирование. |
| Мини-приложение | Логическое приложение со стабильным `id`. |
| Черновик | Изменяемая рабочая копия мини-приложения. |
| Релиз | Неизменяемая исполняемая версия мини-приложения. |
| Bundle | JSON-программа и необходимые скрипты, skills, MCP-компоненты и другие файлы. |
| Интерпретатор | Движок, проверяющий и исполняющий bundle. |
| Оператор | Человек, заполняющий входы, подтверждающий действия и получающий результат. |
| Автор | Ответственный за мини-приложение пользователь; определяется автоматически и редактируется. |
| Запуск | Одно тестовое выполнение черновика или выполнение релиза. |

## 5. Основные принципы

1. **Создается из сессии, не зависит от сессии.** Сессия является входом
   дистилляции, но не runtime-зависимостью.
2. **Переносимый программный контракт.** Поведение задается версионируемым
   JSON-файлом, а не состоянием UI или неявным диалогом FoxxyCode.
3. **Генерируется, но редактируется.** FoxxyCode предлагает поля, шаги, промпты,
   критерии успеха и отображение; человек может изменить их.
4. **Явная недетерминированность.** Каждый вызов LLM или агента объявляется
   отдельным шагом. Остальной workflow остается детерминированным.
5. **Явное взаимодействие с оператором.** Вопросы и подтверждения во время
   выполнения существуют только как объявленные шаги.
6. **Минимальные полномочия.** Доступ к файлам, процессам, сети, секретам, MCP и
   моделям объявляется до запуска.
7. **Нет скрытого происхождения в релизе.** Релиз не хранит id исходной сессии,
   транскрипт, историю tool-call’ов или использованную в сессии модель.
8. **Релиз контролируется человеком.** Очистка и выпуск в MVP всегда требуют
   проверки человеком.
9. **Общая семантика выполнения.** FoxxyCode и автономный executable используют
   одно ядро валидации и интерпретации.
10. **Безопасная операторская поверхность.** Рассуждения агента и raw tool
    traffic являются внутренними деталями. Оператор видит объявленные вопросы,
    подтверждения, безопасные статусы шагов, результаты и артефакты, а
    диагностика записывается в выбранную директорию запуска приложения.

## 6. Высокоуровневая архитектура

Функциональность состоит из шести логических компонентов.

### 6.1 Дистиллятор

Дистиллятор — асинхронный процесс FoxxyCode, который:

- читает явно выбранную сессию;
- определяет задачу, успешный путь, повторные попытки, неудачные эксперименты,
  фактические входы, выходы и неявные требования к окружению;
- превращает стабильные значения в константы, а изменяемые — во входы оператора;
- превращает наблюдавшиеся действия в типизированные шаги workflow;
- копирует или создает необходимые скрипты и переносимые ресурсы;
- копирует необходимые skills и переносимые MCP-компоненты в draft bundle;
- предлагает зависимости, разрешения, критерии успеха и renderer’ы;
- классифицирует каждый source artifact как operator input, bundled asset, test
  fixture, expected output example либо discarded evidence;
- сохраняет source duration, model/API time и input/output token counts как
  приватные authoring evidence, когда они доступны;
- удаляет секреты и данные, специфичные для исходной сессии;
- запускает и исправляет черновик на fixture исходной сессии.

Приватная задача дистилляции может ссылаться на исходную сессию, пока она
выполняется. Ссылка должна удаляться после завершения или удаления задачи и
никогда не должна попадать в released bundle.

Принятый session result, candidate artifacts, обнаруженные requirements и
очищенный source transcript могут показываться read-only в workspace
дистилляции. Это evidence для автора и refinement, а не workflow steps или
состояние portable-программы.

### 6.2 Каталог и хранилище

Каталог индексирует локальные черновики и релизы в конфигурационной директории
FoxxyCode. Он предоставляет список, текстовый поиск, теги, статус, версии и
базовую измеренную длительность запуска. Семантический/векторный поиск может
быть добавлен позднее.

Один источник каталога используется и полным разделом **Мини-приложения**, и
компактным drawer, который открывается без выхода из сессии. Drawer является
быстрой поверхностью поиска/запуска, а не отдельной копией состояния.

### 6.3 Редактор

Редактор предоставляет:

- метаданные приложения;
- упорядоченный collapsible workflow navigator с номером, type badge, title и
  validation state шага;
- read-only область source result/evidence только на этапе дистилляции;
- preview сгенерированной формы ввода;
- визуальную структуру workflow;
- настройки отдельных шагов;
- редактирование исходного JSON;
- управление файлами bundle;
- проверку зависимостей и разрешений;
- критерии успеха;
- настройку отображения результата;
- тестовые запуски и логи;
- результаты очистки;
- управление релизом.

Визуальное и JSON-редактирование изменяют один канонический черновик.

На широком экране workspace дистилляции может состоять из трех функциональных
областей: workflow/source evidence, structured editor и refinement assistant.
На узком экране те же области становятся tabs или drawers. Это контракт
поведения, а не требование копировать размеры или визуальный стиль референса.

Refinement assistant может предложить добавление, удаление, перестановку и
изменение steps, inputs, prompts, dependencies, permissions, success checks и
result display. Каждый ответ создает проверяемый patch к точной
`draft_revision`; автор принимает или отклоняет его до изменения canonical
draft. Refinement conversation, label его модели и source context являются
authoring-only данными и не попадают в `miniapp.json` или export.

### 6.4 Ядро runtime

Ядро runtime валидирует схему, разрешает ссылки, вычисляет ограниченные условия,
исполняет шаги, записывает события, контролирует разрешения, проверяет выходы и
строит объявленное представление результата.

Оно должно находиться ниже слоя интеграции с web/desktop, чтобы одно ядро могли
использовать:

- процесс FoxxyCode для web/desktop;
- автономный command-line executable.

### 6.5 Интерпретатор и builder executable

При сборке с `-tags miniapps` основной executable `foxxycode` становится
каноническим интерпретатором и builder:

```text
foxxycode miniapps validate <miniapp.json|bundle>
foxxycode miniapps inspect <miniapp.json|bundle>
foxxycode miniapps requirements <miniapp.json|bundle>
foxxycode miniapps run <miniapp.json|bundle> [--input inputs.json]
foxxycode miniapps run --program - --input inputs.json
foxxycode miniapps build <miniapp.json|bundle> \
  --mode console|ui \
  --target windows/amd64 \
  --output <path> \
  --log-scope local|global
```

`--program -` читает JSON-программу из stdin. Неинтерактивный запуск получает
все обязательные inputs через `--input` или объявленные bindings, пишет
machine-readable progress в stderr и JSON результата в stdout. Интерактивный
console-run показывает объявленные поля как терминальные prompts. Для него не
нужны HTTP server, embedded SPA или desktop build tags.

Builder создает app-specific executable:

- `console` сохраняет console subsystem целевой ОС. При наличии TTY он
  запрашивает недостающие declared inputs, иначе работает headless;
- `ui` поднимает доступный только на loopback mini-app HTTP endpoint и открывает
  существующую desktop-оболочку FoxxyCode сразу на app-run route. Страница
  строится по JSON-описанию inputs и display и не показывает обычный
  chat/session UI;
- оба режима выполняют один embedded JSON и bundle через общее ядро runtime;
- оба режима скрывают model reasoning, внутренние сообщения агента и raw tool
  calls. Выводятся или отображаются только operator-visible events.

Первая цель UI executable — `windows/amd64`, соответствующая существующей
desktop-оболочке WebView2. Console targets могут добавляться для совместимых
комбинаций `GOOS/GOARCH`, если выбранные steps и dependencies переносимы.

#### 6.5.1 Стратегия упаковки на Go

В v1 builder использует compile-time embedding, а не модификацию уже
слинкованного executable:

1. валидирует, очищает, канонизирует и фиксирует integrity входного bundle;
2. создает изолированный временный build workspace с version-matched исходным
   кодом mini-app runner и vendored build dependencies;
3. помещает канонический `.foxxyapp` payload в этот workspace и подключает его к
   runner через Go `//go:embed`;
4. вызывает контролируемый `go build` с `-tags miniapps` и tags выбранного
   режима;
5. для Windows `ui` добавляет `-tags "miniapps http ui desktop"` и linker option
   `-H=windowsgui`; для `console` не использует `windowsgui`;
6. запускает `inspect` для собранного executable и проверяет digest embedded
   manifest до сообщения об успехе.

Подход использует стандартные механизмы Go:
[`embed`](https://pkg.go.dev/embed),
[build constraints](https://pkg.go.dev/cmd/go#hdr-Build_constraints) и
linker option
[`-H windowsgui`](https://pkg.go.dev/cmd/link), разделяющий Windows console и
GUI binaries.

Builder может использовать уже установленный совместимый Go toolchain либо
скрыто установить checksum-locked portable Go toolchain в runtime cache
FoxxyCode по проверенной политике `silent_private`. Он не должен зависеть от
наличия developer checkout репозитория. Шаблон/исходники runner и все
необходимые module sources должны
совпадать с версией FoxxyCode, выполняющей сборку. UI template содержит
предварительно собранные version-matched SPA assets, поэтому сборка конкретного
мини-приложения не требует Node.js или npm.

Результат — один распространяемый файл приложения, содержащий интерпретатор,
`miniapp.json`, bundle files, skills, portable MCP assets и необязательные UI
assets. Компоненты, которым необходимы реальные файлы, проверяются и при первом
запуске извлекаются в app-specific runtime cache. Host dependencies и
компоненты, которые нельзя законно распространять, остаются явными preflight
requirements.

Для Windows UI формулировка «один executable» не означает, что WebView2 Runtime
скомпилирован внутрь файла. Приложение использует Evergreen WebView2 Runtime,
проверяет его наличие до открытия окна и соблюдает документированные Microsoft
[правила распространения WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).
Fixed Version runtime может быть явно разрешенной bundled dependency, но
извлекается и управляется отдельно.

### 6.6 Хранилище запусков

Каждый тестовый и обычный запуск получает id и сохраняет:

- id мини-приложения и версию релиза либо ревизию черновика;
- время начала и завершения;
- фактические входы без секретов;
- события шагов и логи;
- подтверждения и ответы оператора;
- результаты и пути созданных артефактов;
- результаты проверок успеха;
- длительность и финальный статус.

Секретные значения никогда не сохраняются в истории запусков.

Корень запуска выбирается для приложения или build profile:

```text
# global
$FOXXYCODE_HOME/apps/<app-slug>--<short-id>/runs/<run-id>/

# local
<run-workspace>/.foxxycode/apps/<app-slug>--<short-id>/runs/<run-id>/
```

Обычно `$FOXXYCODE_HOME` равен `~/.foxxycode`. Стабильный suffix id не позволяет
двум приложениям с одинаковым display name использовать общую директорию.
`local` требует явно выбранного run workspace; UI executable без workspace
должен запросить его либо перейти на `global` согласно проверенному build
profile.

Каждая директория запуска содержит как минимум:

```text
run.json
events.jsonl
execution.log
artifacts/
runtime/
```

Console и UI operator streams содержат только lifecycle, безопасный progress,
declared interaction, validation, result и artifact events. Raw
chain-of-thought/reasoning не отображается и не сохраняется. Tool invocations
отсутствуют в операторском потоке; `events.jsonl` может сохранять tool name,
step id, начало/завершение, duration, outcome и только явно разрешенные
redacted/truncated arguments или results. Значения с секретами удаляются до
записи в любой sink, включая diagnostic logs.

## 7. Структура хранилища и bundle

Глобальная директория каталога и запусков:

```text
$FOXXYCODE_HOME/apps/
```

где `$FOXXYCODE_HOME` — общая конфигурационная директория FoxxyCode, обычно
`~/.foxxycode`.

Приложение также может быть локальным для явно выбранного workspace в
`<workspace>/.foxxycode/apps/`. Структура внутри любого из этих корней:

```text
apps/
  <app-slug>--<short-id>/
    app.json
    draft/
      miniapp.json
      files/
      skills/
      mcp/
      fixtures/
      sanitization.json
    releases/
      1.0.0/
        miniapp.json
        files/
        skills/
        mcp/
        manifest.lock.json
    runs/
      <run-id>/
        run.json
        events.jsonl
        execution.log
        artifacts/
        runtime/
```

`app.json` содержит изменяемые метаданные каталога и указатели на текущий
черновик/релиз. `miniapp.json` является переносимой программой.

Экспортированный bundle представляет собой один архив с рекомендуемым
расширением `.foxxyapp`. Это ZIP-совместимый контейнер с `miniapp.json` в корне.
Перед распаковкой импортируемого архива обязательны проверки traversal,
максимального размера, количества файлов, symlink и дублирующихся путей.

## 8. Жизненный цикл и версии

### 8.1 Черновик

- Новая дистилляция создает изменяемый черновик.
- Редактирование черновика не меняет версию релиза.
- Каждое успешное сохранение увеличивает внутренний `draft_revision`.
- Тестовый запуск содержит точную ревизию черновика.
- Черновик может существовать одновременно с последним релизом.

### 8.2 Релиз

- Релиз создает неизменяемую семантическую версию.
- Первый релиз по умолчанию получает версию `1.0.0`.
- Редактирование released-приложения создает или изменяет его черновик, но
  никогда не меняет файлы релиза.
- Для выпуска измененного черновика требуется повысить версию.
- Редактор предлагает:
  - patch для промптов, отображения, проверок и совместимых исправлений;
  - minor для обратно совместимых входов, выходов или шагов;
  - major для удаленных/переименованных входов, измененных контрактов выхода
    или несовместимой семантики выполнения.
- Автор может изменить предложение, но повторная или меньшая версия запрещена.

В MVP существуют только состояния `draft` и `released`.

## 9. Процесс дистилляции

### 9.1 Условия запуска

**Создать мини-приложение** доступно, когда:

- сессия существует и доступна для чтения;
- в сессии сейчас не выполняется turn;
- сессия содержит хотя бы одну завершенную задачу и результат ассистента;
- текущий интерфейс — web или desktop.

Пользователь видит предупреждение, что данные сессии будут проанализированы, а
тест может повторить действия. Тест не выполняет внешние побочные эффекты, пока
не приняты запрошенные разрешения.

### 9.2 Выбор сценария

Дистиллятор анализирует всю сессию, но создает один конкретный сценарий на
черновик. Он должен:

1. определить вероятную задачу и финальный принятый результат;
2. исключить неудачные эксперименты, если они не нужны как fallback;
3. показать краткое описание сценария для подтверждения;
4. позволить исправить задачу или ожидаемый результат до генерации.

Если в сессии есть две независимые задачи, дистиллятор просит выбрать одну и не
объединяет их молча.

### 9.3 Определение входов

Дистиллятор классифицирует значения сессии как:

- постоянные константы workflow;
- входы оператора;
- секреты из runtime bindings;
- значения, получаемые предыдущими шагами;
- требования к окружению;
- случайные данные исходной сессии, которые нужно удалить.

Фактические значения исходной сессии сохраняются только в локальном test
fixture. Обнаруженные в fixture секреты заменяются ссылками на secret bindings.

### 9.4 Синтез workflow

Наблюдавшиеся tool-call’ы и модельные действия преобразуются в минимальный явный
workflow, воспроизводящий успешный путь. Повторяющееся агентское рассуждение
следует заменять детерминированными шагами, если сессия дает для этого достаточно
информации. Агентский шаг сохраняется только там, где требуется динамическое
планирование.

### 9.5 Тестирование и исправление

Первый тест использует те же фактические входы и изолированные копии необходимых
исходных файлов. Дистиллятор может выполнять несколько итераций:

1. проверить bundle и требования;
2. создать изолированный test workspace;
3. выполнить workflow;
4. проверить критерии успеха;
5. сравнить объявленные выходы с ожидаемым результатом исходной сессии;
6. исправить черновик;
7. повторять до успеха или лимита.

Дистилляция, достигшая лимита, остается черновиком и показывает неуспешные шаги
и критерии. Автоматический релиз запрещен.

### 9.6 Очистка и проверка

Перед релизом FoxxyCode проверяет весь JSON и каждый файл bundle на:

- API-ключи, access token’ы, cookie, пароли и приватные ключи;
- абсолютные пользовательские пути;
- id исходной сессии и фрагменты транскрипта;
- персональные или чувствительные данные;
- специфичные для окружения endpoint’ы и id аккаунтов;
- ссылки на файлы, не включенные в bundle;
- необъявленные процессы, сетевые хосты, модели, skills или MCP-серверы.

Результаты отображаются на экране проверки релиза. Блокирующие замечания нужно
устранить, неблокирующие — явно подтвердить.

## 10. Контракт JSON-программы

### 10.1 Общие правила

- Файл использует UTF-8 JSON.
- `schema_version` версионируется по SemVer.
- Неизвестная обязательная major-версия отклоняется.
- В объектах, влияющих на безопасность, неизвестные поля по умолчанию
  запрещены.
- Каждый шаг workflow имеет уникальный `id`.
- Шаги выполняются последовательно, кроме выбора вложенного пути через `branch`.
- Runtime-значения являются JSON-совместимыми значениями либо типизированными
  file/directory handles.
- Интерпретатор проверяет всю программу до первого шага с побочным эффектом.
- JSON является каноническим источником поведения; визуальный редактор не
  хранит второй вариант программы.
- Универсальные вычисления выражаются только версионированным шагом `program`.
  Его обращения к хосту возможны только через объявленные типизированные imports.

### 10.2 Верхний уровень

```json
{
  "schema_version": "1.0.0",
  "kind": "foxxycode.miniapp",
  "id": "weekly-repository-report",
  "version": "1.0.0",
  "state": "released",
  "metadata": {},
  "requirements": {},
  "permissions": {},
  "inputs": [],
  "workflow": [],
  "success": {},
  "outputs": [],
  "display": {},
  "runtime": {
    "log_scope": "global",
    "operator_event_level": "status",
    "diagnostic_tool_events": "sanitized",
    "persist_agent_reasoning": false
  }
}
```

В переносимом черновике `version` отсутствует либо заменяется маркером вида
`0.0.0-draft.<revision>`.

### 10.3 Метаданные

```json
{
  "metadata": {
    "name": "Weekly repository report",
    "description": "Builds and summarizes a repository activity report.",
    "goal": "Produce a verified weekly report from operator-selected inputs.",
    "author": "Detected User",
    "tags": ["reporting", "git"],
    "estimated_duration_seconds": 90
  }
}
```

Автор по возможности определяется из локального окружения пользователя и может
редактироваться. Происхождение из исходной сессии намеренно отсутствует.
`description` объясняет приложение пользователю каталога, а `goal` определяет
результат, который должен обеспечить дистиллированный workflow.

### 10.4 Ссылки на значения

Типизированные ссылки используют объект и сохраняют JSON-тип значения:

```json
[
  { "$ref": "inputs.repository" },
  { "$ref": "steps.collect.outputs.items" },
  { "$ref": "secrets.github_token" }
]
```

Строковые шаблоны используют:

```text
Report for {{ inputs.period }} contains {{ steps.collect.outputs.count }} items.
```

Корневые пространства ссылок v1:

- `inputs.<id>`;
- `steps.<step-id>.outputs.<name>`;
- `secrets.<id>`;
- `run.id`, `run.workspace` и `run.output_dir`;
- `app.id` и `app.version`.

Ссылка на необъявленное или еще не созданное значение является ошибкой
валидации. Секреты разрешено передавать в одобренные поля выполнения, но
запрещено интерполировать в логи, display-шаблоны и сохраняемые результаты.

### 10.5 Ограниченные условия

Условия являются данными, а не JavaScript- или shell-выражениями:

```json
{
  "op": "and",
  "args": [
    {
      "op": "gt",
      "left": { "$ref": "steps.collect.outputs.count" },
      "right": 0
    },
    {
      "op": "eq",
      "left": { "$ref": "inputs.include_details" },
      "right": true
    }
  ]
}
```

Обязательные операторы v1: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `and`, `or`,
`not`, `exists`, `empty`, `contains` и `matches`. `matches` использует
ограниченную runtime-реализацию регулярных выражений.

### 10.6 Видимость runtime и политика логов

`runtime.log_scope` имеет значение `local` или `global` и выбирает правило
run-root из раздела 6.6. В schema v1 `operator_event_level` фиксирован как
`status`. `diagnostic_tool_events` поддерживает `none`, `metadata` и
`sanitized`.
`miniapps build --log-scope` переопределяет portable default для создаваемого
executable и записывает выбор в его embedded build manifest.

В v1 `persist_agent_reasoning` обязан быть `false`. Raw model reasoning,
chain-of-thought, assistant scratch content, unredacted tool arguments и
unredacted tool results запрещены в console output, UI events, HTTP/SSE
operator streams, run history и log files. Это не скрывает объявленный результат
agent step: шаг должен вернуть явный typed output и безопасный operator summary.

## 11. Генерируемые входы и элементы формы

Каждый вход разделяет семантику данных и представление:

```json
{
  "id": "format",
  "type": "string",
  "title": "Report format",
  "description": "Select the generated report format.",
  "required": true,
  "default": "markdown",
  "validation": {
    "enum": ["markdown", "json", "table"]
  },
  "ui": {
    "control": "radio",
    "order": 30
  },
  "visible_when": {
    "op": "eq",
    "left": { "$ref": "inputs.generate_report" },
    "right": true
  }
}
```

### 11.1 Типы входов

MVP поддерживает:

- `string`;
- `text`;
- `integer`;
- `number`;
- `boolean`;
- `date`;
- `datetime`;
- `enum`;
- `file`;
- `files`;
- `directory`;
- `secret`.

### 11.2 UI-контролы

MVP поддерживает:

- однострочный text input;
- многострочный textarea;
- numeric input;
- checkbox;
- select;
- radio group;
- date/datetime picker;
- file picker;
- multi-file picker;
- directory picker;
- secret/password input.

Первоначальный control выбирает дистиллятор. Автор может изменить control, если
он совместим с типом входа.

### 11.3 Валидация и зависимости

Поддерживаемая валидация:

- обязательность;
- минимум и максимум;
- минимальная и максимальная длина;
- enum;
- regex pattern;
- допустимые расширения файлов и media type;
- максимальное число файлов и общий размер;
- существование пути и проверка file/directory;
- `visible_when`, `enabled_when` и `required_when`.

Граф зависимостей входов должен быть ацикличным.

## 12. Семантика workflow

### 12.1 Общие поля шага

```json
{
  "id": "step-id",
  "kind": "script",
  "title": "Human-readable label",
  "when": { "op": "exists", "value": { "$ref": "inputs.source" } },
  "timeout_seconds": 120,
  "retry": {
    "max_attempts": 2,
    "backoff_seconds": 2
  },
  "on_error": "fail",
  "redact": ["token"]
}
```

`on_error` поддерживает `fail`, `continue` и `fallback`. Fallback содержит явный
вложенный список `steps`. Шаг получает статус `pending`, `running`, `waiting`,
`succeeded`, `failed`, `skipped` или `cancelled`.

### 12.2 Шаг ввода оператора

Верхнеуровневые входы собираются до выполнения. Шаг `operator_input` получает
данные, которые становятся известны только после предыдущих результатов:

```json
{
  "id": "choose_candidate",
  "kind": "operator_input",
  "fields": [
    {
      "id": "candidate",
      "type": "enum",
      "options": { "$ref": "steps.discover.outputs.candidates" },
      "ui": { "control": "radio" }
    }
  ]
}
```

### 12.3 Скрипт и внешняя команда

```json
{
  "id": "collect",
  "kind": "script",
  "runtime": "python",
  "runtime_version": "3.12",
  "source": {
    "type": "bundle",
    "path": "files/collect.py"
  },
  "args": [
    "--repository",
    { "$ref": "inputs.repository" }
  ],
  "env": {
    "API_TOKEN": { "$ref": "secrets.api_token" }
  },
  "outputs": {
    "protocol": "json",
    "schema": {
      "type": "object",
      "required": ["count", "items"]
    }
  }
}
```

`source.type` поддерживает:

- `inline` с полем `code`;
- `bundle` с безопасным относительным `path`;
- `command` с именем executable и массивом аргументов.

Неявная shell-конкатенация запрещена. Команда запускается как executable и
массив аргументов. Если требуется shell-синтаксис, shell явно объявляется как
зависимость и разрешение.

### 12.4 Агентский шаг

```json
{
  "id": "prepare_summary",
  "kind": "agent",
  "model": {
    "binding": "primary"
  },
  "system_prompt": "Produce a factual report from the supplied data.",
  "prompt": "Summarize:\n{{ steps.collect.outputs.items }}",
  "tools": ["bundle.skill.report-format"],
  "max_turns": 4,
  "output_schema": {
    "type": "object",
    "required": ["title", "markdown"]
  }
}
```

Агентский шаг имеет ограниченное число turn’ов и явный allowlist инструментов.
Он не наследует текущую сессию FoxxyCode, проектные инструменты, rules, memory
или MCP-подключения.

### 12.5 HTTP API-шаг

Шаг `api` объявляет method, шаблонизированный URL, headers, query, body,
допустимые status code, timeout, retry, декодирование ответа и output schema.
Хост должен соответствовать сетевым разрешениям. Секретные headers скрываются.

### 12.6 Шаги MCP и skill

- Шаг `mcp` вызывает tool включенного в bundle MCP-компонента по стабильным id
  сервера и tool.
- Шаг `skill` вызывает entry point включенного в bundle skill через mini-app
  harness.
- Bundle содержит требуемый skill и переносимые MCP-файлы либо фиксированное
  проверяемое требование.
- Внешние credentials остаются runtime secret bindings.
- MCP-сервер, который нельзя распространять, объявляется как host requirement,
  а не копируется.

### 12.7 Файловая операция

Шаг `file` поддерживает явные операции `read`, `write`, `copy`, `move`, `mkdir`,
`list` и `archive`. Разрушительные операции и запись вне run workspace требуют
объявленных разрешений и, при соответствующей настройке, подтверждения. Пути
используют типизированные handles или нормализованные пути внутри разрешенных
корней.

### 12.8 Подтверждение

```json
{
  "id": "approve_publish",
  "kind": "confirm",
  "title": "Publish generated files?",
  "message": "The mini app will write {{ steps.render.outputs.count }} files.",
  "details": { "$ref": "steps.render.outputs.preview" },
  "required": true,
  "reject": "cancel"
}
```

Интерпретатор переходит в `waiting` до ответа оператора. Headless-запуск
останавливается до начала выполнения, если для обязательного взаимодействия не
задана политика ответа.

### 12.9 Условная ветвь

```json
{
  "id": "select_rendering",
  "kind": "branch",
  "if": {
    "op": "eq",
    "left": { "$ref": "inputs.format" },
    "right": "markdown"
  },
  "then": [],
  "else": []
}
```

Выполняется только выбранная ветвь. Id вложенных шагов остаются глобально
уникальными.

### 12.10 Вызов мини-приложения

Шаг `miniapp` вызывает точные id и released-версию мини-приложения с
сопоставленными входами и именованными выходами. Диапазоны версий и зависимости
от draft запрещены в released bundle для воспроизводимости.

### 12.11 Универсальный программный шаг в JSON

Шаг `program` содержит JSON-native стековый язык инструкций. Идентификатор языка
MVP — `foxxy-vm/1`. Язык поддерживает функции, локальные значения, циклы,
условные переходы, исключения, массивы, объекты, строки, числа, boolean, null и
вызовы явно импортированных возможностей хоста. Это универсальный язык
программирования, а не только формат выражений для условий.

Пример:

```json
{
  "id": "copy_items",
  "kind": "program",
  "language": "foxxy-vm/1",
  "entry": "main",
  "imports": {},
  "functions": {
    "main": [
      { "op": "ref.get", "arg": "inputs.items" },
      { "op": "local.set", "arg": "items" },
      { "op": "const", "arg": 0 },
      { "op": "local.set", "arg": "index" },
      { "op": "const", "arg": [] },
      { "op": "local.set", "arg": "result" },
      { "op": "label", "arg": "loop" },
      { "op": "local.get", "arg": "index" },
      { "op": "local.get", "arg": "items" },
      { "op": "array.len" },
      { "op": "lt" },
      { "op": "jump_if_false", "arg": "done" },
      { "op": "local.get", "arg": "result" },
      { "op": "local.get", "arg": "items" },
      { "op": "local.get", "arg": "index" },
      { "op": "array.get" },
      { "op": "array.push" },
      { "op": "local.set", "arg": "result" },
      { "op": "local.get", "arg": "index" },
      { "op": "const", "arg": 1 },
      { "op": "add" },
      { "op": "local.set", "arg": "index" },
      { "op": "jump", "arg": "loop" },
      { "op": "label", "arg": "done" },
      { "op": "local.get", "arg": "result" },
      { "op": "return" }
    ]
  },
  "limits": {
    "instructions": 1000000,
    "wall_time_seconds": 30,
    "heap_bytes": 67108864,
    "stack_depth": 1024,
    "call_depth": 128
  },
  "output_schema": {
    "type": "array"
  }
}
```

Обязательные группы инструкций:

- стек и значения: `const`, `ref.get`, `local.get`, `local.set`, `dup`, `swap`
  и `pop`;
- арифметика, сравнение, boolean-, string-операции и явные преобразования;
- создание, чтение, изменение и обход массивов и объектов;
- управление: labels, переходы, условные переходы, вызов/возврат функций и
  структурированные `try`/`throw`;
- проверка по JSON Schema и возврат типизированного результата;
- `host.call` только через id объявленного import.

До выполнения валидатор разрешает все labels и функции, отклоняет неизвестные
opcodes и неверные цели стека/переходов, проверяет imports и требует конечные
положительные лимиты в рамках политики движка. VM расходует лимит инструкций и
соблюдает ограничения wall time, heap, stack, call depth и отмену. Исчерпание
любого лимита предсказуемо завершает шаг ошибкой.

По умолчанию VM является чистой и детерминированной. Побочные эффекты возможны
только через `host.call`. Import сопоставляет стабильный id с существующей
возможностью мини-приложения: файловой операцией, HTTP-запросом, командой,
MCP/skill-вызовом, модельным вызовом, временем или источником случайности. Каждый
import имеет typed input/output schema и проходит через те же permissions,
secrets, redaction, timeout и logging, что и обычный workflow step. Нет `eval`,
динамической загрузки opcodes или неявного доступа к процессам, файлам и сети.
Ограниченный язык условий из раздела 11 остается отдельным и не выполняет
побочные эффекты.

## 13. Зависимости и portable runtime

`requirements` объявляет:

- операционные системы и CPU-архитектуры;
- версию движка-интерпретатора;
- необходимые executable;
- языковые runtime, например Python или Go;
- portable runtime packages;
- переменные окружения и secret bindings;
- model bindings с точными providers/models либо требованиями к возможностям;
- сетевое подключение;
- включенные в bundle или предоставляемые хостом MCP-серверы и skills.

Пример:

```json
{
  "requirements": {
    "engine": ">=1.0.0 <2.0.0",
    "platforms": ["windows/amd64", "linux/amd64"],
    "runtimes": [
      {
        "id": "python",
        "version": "3.12.x",
        "provision": {
          "mode": "portable",
          "interaction": "silent_private",
          "url": "https://example.invalid/python.zip",
          "sha256": "<required checksum>",
          "size_bytes": 52428800,
          "install_script": "files/install-python.ps1"
        }
      }
    ],
    "model_bindings": [
      {
        "id": "primary",
        "selection": "fixed",
        "provider": {
          "type": "openai",
          "base_url": "https://api.openai.com/v1",
          "scope": "remote"
        },
        "model": "exact-api-model-id",
        "credentials": {
          "source": "matched_provider"
        },
        "required_capabilities": ["responses", "tools"]
      },
      {
        "id": "local_summary",
        "selection": "fixed",
        "provider": {
          "type": "openai",
          "base_url": "http://127.0.0.1:11434/v1",
          "scope": "local",
          "adapter": "ollama"
        },
        "model": "exact-local-model-tag",
        "local_bootstrap": {
          "connect": true,
          "start": "if_declared",
          "ensure_model": "pull_if_missing",
          "load": "if_supported",
          "storage_scope": "app_cache",
          "timeout_seconds": 300
        }
      }
    ]
  }

```

### 13.1 Скрытая приватная установка

Правила provisioning:

- уже установленный runtime переиспользуется, только если это допускают
  объявленные правила совместимости и integrity;
- `interaction: "silent_private"` выполняет preflight-установку без отдельного
  запроса во время запуска;
- скрытая установка может писать только в runtime cache приложения и staging
  directory на той же файловой системе; запрещены admin/root elevation,
  системные package managers, установка services, глобальное изменение
  `PATH`/registry и запись за пределами приватного cache;
- каждая загрузка имеет проверенный HTTPS source, точный checksum, ожидаемый
  размер или его лимит и зафиксированный artifact identity;
- декларативные действия unpack/install и bundled install script видны на
  release/import review и выполняются в уже утвержденных network, process и
  filesystem permissions приложения;
- принятие или запуск точно проверенного release разрешает его объявленный
  silent-private preflight; новый запрос нужен только при расширении полномочий
  новой версией, изменении незафиксированного source или явно объявленном
  взаимодействии;
- provisioning транзакционен: загрузка и проверка проходят в staging, успешный
  результат атомарно активируется, параллельные установки блокируются, ошибка
  не повреждает предыдущий cache;
- операторский интерфейс может показывать только безопасный статус
  **Подготовка среды приложения**; подробная redacted-диагностика пишется в run
  log приложения;
- точные разрешенные версии и digests записываются в `manifest.lock.json`;
- файлы релиза и зафиксированные зависимости проверяются по integrity перед
  запуском;
- если зависимость нельзя подготовить в этих границах, preflight завершается
  ошибкой без elevation и системного fallback.

Те же правила применяются при извлечении bundled runtime из собранного executable
и загрузке модели локальным провайдером. Повторное использование cache требует
точного зафиксированного digest либо явно разрешенного правила совместимости.

### 13.2 Привязки providers и models

Agent- или model-step ссылается на id привязки:

```json
{
  "id": "prepare_summary",
  "kind": "agent",
  "model": {
    "binding": "primary"
  }
}
```

`selection: "fixed"` связывает шаг с одной identity провайдера и одним точным
API model id этого провайдера. Интерпретатор не заменяет его похожей, новой,
дешевой или доступной локально моделью. Альтернативные модели разрешены только
как объявленный автором упорядоченный fallback из явных binding ids.
`selection: "capability"` сохраняет выбор по возможностям для приложений, где
автор намеренно его разрешил.

Провайдер разрешается по следующему алгоритму:

1. Нормализовать эффективный `base_url` binding: привести scheme и host к
   нижнему регистру, host — к ASCII-форме, убрать стандартный порт, нормализовать
   dot-segments и один завершающий slash. User information, query и fragment
   запрещены. Path, включая `/v1`, значим.
2. Так же нормализовать `api_base` или документированный native default каждого
   локально настроенного провайдера. Локальное имя конфигурации — alias, а не
   часть identity.
3. Требовать точного совпадения canonical URL. Запрещены prefix, substring, DNS
   и автоматическое отождествление `localhost` с иными loopback-адресами.
4. Для `openai` и `anthropic` также требовать совпадения типа провайдера, потому
   что один gateway URL может предоставлять разные wire protocols. Объявленный
   adapter также должен совпадать.
5. Использовать credential и proxy bindings совпавшей локальной конфигурации;
   API keys и значения credentials никогда не попадают в JSON или bundle.
6. Требовать точный API model id: сначала проверить локально настроенные модели,
   затем поддерживаемый discovery API провайдера. Отсутствие credential, точной
   модели или требуемых capabilities завершает preflight ошибкой.

Для OpenAI discovery выполняется через `GET /v1/models`, возвращающий доступные
model ids ([OpenAI Models API][openai-models-api]). Для Anthropic используется
native List Models API ([Anthropic List Models][anthropic-models-api]).
Generic OpenAI-compatible provider можно проверить через `GET /v1/models`, но
ошибка не разрешает подстановку другой модели.

`scope: "local"` допустим только для canonical loopback host или
поддерживаемого local socket. Адреса private LAN не считаются локальными.
Интерпретатор:

1. проверяет объявленный base URL с коротким timeout;
2. запускает bundled или скрыто подготовленный provider, только если это явно
   разрешают `local_bootstrap.start` и adapter recipe;
3. получает список моделей и ищет точную модель;
4. загружает ее при объявленном `pull_if_missing`, если locked identity, лимит
   диска, network permission и silent-private policy это разрешают;
5. загружает модель в память, когда adapter поддерживает такую операцию;
6. проверяет точный model id и capabilities до первого model-step.

Adapters MVP:

- `ollama`: список через `GET /api/tags`, pull через `POST /api/pull` и вызовы
  через объявленный OpenAI-compatible `/v1` API ([список Ollama][ollama-list],
  [pull][ollama-pull], [совместимость с OpenAI][ollama-openai]);
- `lmstudio`: список через `GET /api/v1/models`, load через
  `POST /api/v1/models/load`, а download — только при объявленной политике
  ([LM Studio REST API][lmstudio-rest], [load endpoint][lmstudio-load]);
- `generic`: только проверка объявленного compatible API; запуск, download и
  load запрещены без отдельно объявленного adapter recipe.

Adapter может вывести native management endpoint из `base_url` только по своей
версионированной встроенной same-origin схеме; нельзя конкатенировать заданный
автором management path. При `storage_scope: "app_cache"` модель разрешено
скачивать только в app-managed provider store внутри приватного cache.
Уже запущенный совпавший provider сразу используется, если точная модель
существует, но интерпретатор не изменяет скрыто его общий model store.

Runtime не угадывает модель по display name. Локальный model tag должен
фиксировать по digest, если provider его предоставляет. Если provider
недоступен, общей установке не хватает модели либо точную модель нельзя
подключить, скачать в разрешенный app store или загрузить, preflight завершается
ошибкой с требуемыми provider identity и model id без раскрытия credentials.

[openai-models-api]: https://developers.openai.com/api/reference/resources/models/methods/list
[anthropic-models-api]: https://platform.claude.com/docs/en/api/models/list
[ollama-list]: https://docs.ollama.com/api/tags
[ollama-pull]: https://docs.ollama.com/api/pull
[ollama-openai]: https://docs.ollama.com/api/openai-compatibility
[lmstudio-rest]: https://lmstudio.ai/docs/developer/rest
[lmstudio-load]: https://lmstudio.ai/docs/developer/rest/load

## 14. Разрешения и секреты

Разрешения задаются декларативно:

```json
{
  "permissions": {
    "filesystem": {
      "read": ["input-files", "selected-directory"],
      "write": ["run-output"]
    },
    "process": ["python", "git"],
    "network": ["api.example.com"],
    "models": ["text-reasoning"],
    "secrets": ["api_token"],
    "operator_confirmation": true
  }
}
```

Runtime показывает эффективные разрешения перед первым запуском и повторно,
когда новая released-версия расширяет полномочия.

Секретные значения:

- передаются оператором, окружением или будущим secret store;
- никогда не копируются из исходной сессии;
- не включаются в экспорт, логи, историю входов, промпты без явной привязки к
  соответствующему полю или отображаемые выходы;
- удаляются из process arguments, если целевой процесс поддерживает stdin или
  переменные окружения.

## 15. Критерии успеха

Успех не равен только нулевому exit code процессов. Мини-приложение объявляет
одну или несколько проверок:

- статус шага;
- JSON Schema результата;
- наличие, тип, размер, checksum или pattern содержимого файла;
- числовой или строковый предикат;
- предикат HTTP status/response;
- модельный judge-промпт со структурированным verdict;
- явное принятие оператором.

Пример:

```json
{
  "success": {
    "mode": "all",
    "checks": [
      {
        "kind": "step",
        "step": "prepare_summary",
        "status": "succeeded"
      },
      {
        "kind": "schema",
        "value": { "$ref": "steps.prepare_summary.outputs.result" },
        "schema": {
          "type": "object",
          "required": ["title", "markdown"]
        }
      },
      {
        "kind": "judge",
        "prompt": "Verify that the report answers the requested period and contains no unsupported claims.",
        "value": { "$ref": "steps.prepare_summary.outputs.result" },
        "output_schema": {
          "type": "object",
          "required": ["passed", "reason"],
          "properties": {
            "passed": { "type": "boolean" },
            "reason": { "type": "string" }
          }
        }
      }
    ]
  }
}
```

Модельные проверки недетерминированы и явно отмечаются в test report. Если
workflow создает структурированный или файловый результат, для релиза требуется
хотя бы одна немодельная структурная проверка.

## 16. Выходы и отображение результата

Каждый выход имеет id, ссылку на значение, тип, опциональную схему, правила
экспорта и renderer. Поддерживаемые типы:

- plain text;
- Markdown;
- JSON;
- table;
- file;
- files;
- directory;
- archive;
- сгенерированные media или другие артефакты генерации.

Поддерживаемые renderer’ы:

- text/Markdown panel;
- JSON tree;
- таблица с объявленными колонками;
- список файлов с preview и download;
- image/audio/video или универсальный preview сгенерированного артефакта, если
  поддерживается media type;
- summary card из именованных выходов.

`display` управляет заголовком, описанием, layout, секциями, свернутыми деталями,
действиями download и основным результатом. Обычный операторский UI не
показывает execution logs inline; для разрешенной локальной диагностики он
может предоставить действие **Открыть папку запуска**. Display-настройки не
могут выполнять код или читать необъявленные файлы.

## 17. Спецификация UI

### 17.1 Действие в сессии

- Кнопка **Создать мини-приложение** показывается в action/header area активной
  сессии только в web и desktop при backend capability `miniapps=true`.
- После завершенного session result то же действие может показываться рядом с
  result summary как **Сохранить как мини-приложение**; обе кнопки запускают одну
  операцию.
- Во время выполняющегося turn кнопка недоступна.
- Нажатие запускает определение сценария и открывает готовый черновик.
- Долгая дистилляция показывает прогресс, текущую фазу, прошедшее время, отмену
  и восстанавливаемое описание ошибки.

### 17.2 Раздел «Мини-приложения»

Основная навигация получает раздел **Мини-приложения** с концептуальными
маршрутами:

```text
#/miniapps
#/miniapps/new
#/miniapps/<id>
#/miniapps/<id>/edit
#/miniapps/<id>/runs/<run-id>
```

Каталог показывает статус, последнюю версию, автора, теги, последний запуск,
измеренную длительность и действия для запуска, редактирования черновика,
создания новой версии, экспорта, импорта и просмотра истории.

Из открытой сессии каталог можно показать в закрываемом quick drawer без
навигации на другой экран. Drawer содержит поиск по name/tags и явный control
**Показывать архивные**. Компактная карточка показывает как минимум:

- icon или сгенерированную отметку media type;
- name и короткое description;
- точную release version и число объявленных inputs;
- compatibility/availability и измеренную duration, когда она известна;
- основное действие **Запустить**;
- overflow menu для edit/new version, history, export и archive/restore.

**Запустить** открывает сгенерированную форму точной разрешенной версии.
Карточка не выполняет побочные эффекты до input validation и preflight.

### 17.3 Редактор

Редактор содержит представления:

- Обзор;
- Входы и live preview формы;
- Workflow;
- Зависимости и разрешения;
- Проверки успеха;
- Результаты/отображение;
- Файлы bundle;
- JSON;
- Тестовые запуски;
- Проверка релиза.

Невалидный raw JSON не заменяет последнюю валидную каноническую версию, пока не
будет распознан и провалидирован. Ошибка указывает и место в JSON, и
соответствующее поле визуального редактора.

Во время дистилляции редактор также предоставляет:

- упорядоченный collapsible список шагов с type badges и отдельно обозначенным
  authoring/system context item;
- read-only карточку **Результат сессии** с принятым output, обнаруженными
  requirements и candidate artifacts;
- collapsible очищенную панель **Контекст исходной сессии**;
- прямое редактирование name, description, goal, input id/label/type/required,
  validation и acceptance criteria;
- permission summary badges для network, filesystem, process/Git, model, MCP и
  skill с переходом к полным деталям;
- refinement assistant с label authoring model/provider и историей draft patches;
- явные действия **Сохранить черновик**, **Выпустить** и закрыть.

Authoring/system context item не является неявным исполняемым шагом. Он
становится переносимым только после преобразования нужного поведения в явные
prompts, constants, bindings или workflow steps. При закрытии UI предупреждает
о несохраненных локальных невалидных правках; валидный autosaved draft остается
доступным.

### 17.4 Runner

Runner:

1. рисует объявленную форму;
2. валидирует входы и зависимости;
3. показывает permissions;
4. выполняет workflow с безопасными live-статусами и записывает execution logs
   в выбранную run directory;
5. останавливается для объявленного ввода или подтверждения оператора;
6. поддерживает отмену;
7. проверяет критерии успеха;
8. отображает объявленные результаты и артефакты для скачивания;
9. показывает total duration, model/API duration, input/output tokens и
   разрешенные non-secret provider/model binding ids, когда они доступны;
10. предлагает **Запустить снова** с редактируемыми прошлыми входами без
   секретов.

### 17.5 Проверка релиза

Экран релиза показывает:

- предлагаемую версию и влияние на совместимость;
- полный permission diff относительно предыдущего релиза;
- зависимости и install-скрипты;
- включенные skills и MCP-компоненты;
- результаты очистки;
- результат последнего same-data test;
- отчет критериев успеха;
- список файлов bundle и integrity manifest.

Релиз недоступен, пока черновик невалиден, существуют неустраненные блокирующие
замечания очистки или текущая ревизия не имеет успешного теста.

## 19. Выполнение и восстановление

- Запускается только точная ревизия черновика или точная версия релиза.
- Каждый шаг записывает структурированные события start, progress, diagnostic
  log, output, waiting, finish и error. Operator event stream публикует только
  безопасное подмножество, заданное `runtime.operator_event_level`.
- Отмена распространяется на дочерние процессы, HTTP, MCP, модели и вложенные
  мини-приложения.
- Выходы завершенных шагов сохраняются инкрементально.
- Сбой процесса переводит активный запуск в `interrupted`.
- Продолжение возможно только тогда, когда каждый завершенный шаг объявляет
  устойчивый результат, а следующий шаг поддерживает resume. Иначе UI предлагает
  новый запуск с теми же входами без секретов.
- Retry и fallback записываются как отдельные attempts.
- Логи имеют лимиты размера и хранения; артефакты результата — настраиваемые
  квоты.
- Raw reasoning никогда не является run event. Raw tool calls остаются
  внутренними; только проверенный diagnostic level может записать redacted tool
  metadata или payload.

## 20. Повторное использование, изменение и обычный агент

Продукт рассматривает три пути:

1. запустить достаточно подходящее released-мини-приложение;
2. создать новую версию близкого мини-приложения;
3. продолжить обычную агентскую сессию.

В MVP:

- каталог доступен для ручного поиска;
- отображается измеренная длительность запусков;
- путь выбирает пользователь;
- изменение всегда создает черновик новой released-версии;
- FoxxyCode не оценивает автоматически все три пути и не маршрутизирует запрос.

В будущем можно добавить семантические векторы, ожидаемое время, вероятность
успеха, стоимость токенов/денег, риск и организационные сигналы использования.
Автоматический router остается рекомендательным, пока будущая спецификация явно
не разрешит автономный выбор.

## 21. Организационный сбор

Будущий сбор на уровне подразделения/компании соблюдает обязательные правила:

- анализируются только сессии с явным opt-in;
- доступ соответствует организационной границе исходной сессии;
- каждое предложенное мини-приложение проверяет и утверждает человек;
- очистка выполняется до добавления предложения в общий каталог;
- released-артефакт не сохраняет содержимое исходной сессии;
- администраторы могут исключать проекты, пути, инструменты, классы данных и
  сетевые домены;
- пользователи видят, какие данные анализируются, и могут отменить сбор.

Фоновый сбор не входит в MVP.

## 22. Валидация и совместимость

Bundle валиден, только если:

- его major-версия схемы поддерживается;
- id и ссылки уникальны и разрешимы;
- зависимости входов ацикличны;
- каждая вложенная branch/fallback-ветвь валидна;
- требуемые ресурсы существуют и совпадают с integrity manifest;
- требования к runtime и моделям разрешимы;
- permissions покрывают каждый шаг без необъявленных полномочий;
- secret references объявлены и не попадают в запрещенные sinks;
- ссылки выходов и критериев успеха разрешимы;
- версии вложенных released-мини-приложений заданы точно;
- пути не выходят за bundle или разрешенные runtime-корни.

Minor-версии схемы могут добавлять опциональные поля. Major-изменение требует
явной миграции. Импорт никогда не переписывает immutable release на месте.

## 23. Критерии приемки MVP

Функциональность принимается, когда продемонстрировано следующее:

1. Пользователь завершает web/desktop-сессию и нажимает **Создать
   мини-приложение**.
2. Дистиллятор анализирует сессию, подтверждает один сценарий и создает черновик
   без происхождения исходной сессии в переносимой программе.
3. Черновик содержит форму, валидный workflow, requirements, permissions,
   критерии успеха, outputs и display settings.
4. Автор может изменить каждое сгенерированное поле визуально и через JSON.
5. Редактор поддерживает объявленные v1-контролы и зависимости валидации.
6. Интерпретатор исполняет все обязательные v1-типы шагов, условия, retry,
   fallback и вложенное мини-приложение с точной версией.
7. Работают inline-скрипты, bundled-скрипты и явно объявленные внешние команды.
8. Отсутствующие locked-зависимости скрыто устанавливаются в приватный cache
   приложения; нет run-time install prompt, elevation или системных изменений.
9. Same-data test выполняется изолированно и сохраняет отчет об успехе.
10. Черновик с неуспешным тестом нельзя выпустить.
11. Release review обнаруживает тестовые секреты и source-specific пути в JSON
    и файлах bundle.
12. Первый release создает immutable-версию `1.0.0`; изменение создает черновик,
    который можно выпустить только с большей версией.
13. Релиз экспортируется в переносимый bundle и импортируется в другую
    совместимую установку.
14. FoxxyCode и автономный интерпретатор дают эквивалентную семантику
    шагов/выходов для одного bundle и входов.
15. Запуски показывают live progress, объявленное взаимодействие, отмену, логи,
    длительность, результаты, артефакты и повтор.
16. Mini-app UI отсутствует в IDE-интеграциях.
17. Пользователь может вручную запустить, версионировать или проигнорировать
    найденное приложение; автоматический router не выдается за реализованный.
18. Сборка без `miniapps` не содержит команд интерпретатора/builder и mini-app
    HTTP routes и не объявляет UI capability; сборка с tag включает их.
19. FoxxyCode запускает JSON-программу без UI и собирает console и Windows
    desktop-UI executables, содержащие канонические программу и bundle.
20. Console и UI executables показывают только безопасные operator events;
    reasoning и raw tool calls скрыты, а redacted execution diagnostics
    сохраняются в выбранном local или global корне
    `.foxxycode/apps/<app>/runs/<run-id>`.
21. Программа `foxxy-vm/1` с функциями и ограниченным циклом выполняется
    эквивалентно встроенным интерпретатором и собранным executable, а
    необъявленный host call или исчерпание лимита предсказуемо завершается
    ошибкой.
22. Fixed provider/model binding использует локальные credentials только после
    точного совпадения нормализованного `base_url`, типа протокола провайдера и
    API model id; другая модель скрыто не подставляется.
23. Разрешенный local provider проверяется, при необходимости запускается, а его
    точная модель pull/load выполняется по silent-private policy; иначе запуск
    прекращается на preflight без model call.
24. Workspace дистилляции показывает упорядоченный typed step navigator, session
    result, очищенный source context, редактируемые inputs/goal/acceptance
    criteria, permission summaries и refinement assistant без экспорта source
    evidence.
25. Refinement request создает проверяемый patch к точной draft revision; его
    принятие создает новую revision, но не обходит test, sanitization и human
    release gates.
26. Из открытой сессии quick catalog drawer ищет по names/tags, опционально
    показывает archived apps и отображает карточки с точной version, input
    count, description, действием **Запустить** и overflow menu; запуск сначала
    открывает сгенерированную форму.
27. Source-session, test и normal-run views показывают доступные total duration,
    model/API duration и input/output token metrics, а released portable program
    не содержит source-session metrics или provenance.

## 24. Рекомендации по реализации

Когда начнется реализация:

- сначала определить JSON Schema и контракт интерпретатора, затем UI-типы;
- до приема released programs зафиксировать таблицу opcodes `foxxy-vm/1`,
  stack effects, числовую/error-семантику, verifier, учет ресурсов и
  cross-runtime conformance fixtures;
- разместить интерпретатор и валидацию bundle во внутреннем пакете, не зависящем
  от HTTP, desktop или React;
- поместить interpreter, builder, HTTP registration и backend capability за
  `//go:build miniapps`; в сборке без tag capability должна быть false, а
  placeholder commands и routes не должны регистрироваться;
- UI должен проверять backend capability в дополнение к существующей проверке
  web/desktop-versus-IDE surface;
- executable создается в version-matched runner build workspace через
  `//go:embed`, после чего проверяется embedded digest полученного файла;
- до реализации добавить happy path как Gherkin feature в корне репозитория;
- покрыть unit-тестами невалидные схемы, небезопасные архивы, утечки секретов,
  path traversal, расхождения permissions, ошибки VM verifier/limits,
  canonicalization provider URL, разрешение точной модели, rollback provisioning,
  отмену и конфликты версий;
- добавлять HTTP handlers только после storage, validation и runtime;
- синхронно обновлять `external/httpserver/openapi.go`, `docs/http-api.md`,
  `DESIGN.md` и `docs/ui.md`;
- хранить все строки web UI в английском и русском словарях локализации;
- собирать и тестировать UI на базовом Chromium 104;
- перед завершением запускать полный набор тестов и lint репозитория.

## 25. Отложенные решения

Следующие детали можно определить при техническом проектировании без изменения
описанного продуктового контракта:

- финальное имя автономного executable и расширения bundle;
- первые официально поддерживаемые portable-дистрибутивы Python и Go;
- подпись bundle и политика доверенных publishers;
- точные сроки хранения истории и квоты артефактов;
- дополнительные UI targets кроме Windows WebView2 и дополнительные console
  `GOOS/GOARCH` targets;
- точный дизайн семантического поиска и трехстороннего router после MVP.
